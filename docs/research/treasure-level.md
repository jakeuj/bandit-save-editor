# 寶物等級／經驗可行性研究

日期：2026-10-23。基準：V1.0.11.2／Steam build 26126719；公開修改器 v2.11 已發布寶物等級。進度入口：[下一步與目前進度](next-version-plan.md)。提案與待辦：[寶物等級 SDD](../../sdd/archive/2026-10-23-treasure-level/proposal.md)、[任務](../../sdd/archive/2026-10-23-treasure-level/tasks.md)。

## 結論

**有條件 go：既有寶物的原版範圍內等級升降；no-go：寶物經驗編輯。** 原路線圖只看到「宝物升级经验」公式，就推測寶物使用經驗制；本次沿實際呼叫鏈核對後修正這項假設。

目前單次／最大升級走魂魄付款後 y6 加一，品質決定上限；沒有找到寶物經驗的初始化、累加、扣除、餘額或呼叫鏈。名為「宝物升级经验」的函式存在，但整個 project 的同名字串只有定義一處，沒有函式參數引用或直接呼叫。不能據此新增經驗欄位，也不能把未知 y 欄猜成餘額。

go 只表示可採下述規格進入實作及首次獨立驗證。2026-10-23 更新：已依 SDD 完成實作與兩庫各自的首次原生證明（背包／裝備庫與穿戴），本機驗收通過、尚未發布；細節見[任務紀錄](../../sdd/archive/2026-10-23-treasure-level/tasks.md)。以下為研究當時的規格與假設。本輪授權為研究、SDD 與承接流程；下一次明確要求「繼續實作下一版功能」時可依本案 SDD 承接，不必重做研究。

## 1. 欄位、資料與資格

wp 中有 **170 個寶物範本**；等階 T1–T6 分別為 21／25／29／31／31／33 件，全部 category=裝備、kind=宝物、部位 wp6=6。不能套用普通／套裝 T1–T9 或部位 1–4 的限制。

座標為 save[x,y,z]。z7 是背包；z9 是裝備庫／穿戴實體。兩庫相同 y6 語意，但位置與生命週期不同，首次開放應分成兩個證明群組。

| 欄位 | 靜態語意 | 提案處置 |
| --- | --- | --- |

| y2 | 裝備數量，取得寫 1 | 首版要求 1 |

## 2. 升級、上限與經驗假設

E2 的類型判斷是 **OR**：宝物或内丹；不是兩條件同時成立。寶物使用自己的魂魄成本分支：

- 等級上限 cap(Q) = 10 + (Q−1)×5，Q1–Q6 對應 10／15／20／25／30／35。
- 當前等級 L、等階 T 的單次成本 C(L,T) = round(10×1.04^((T−1)×30+4L)−1)（V1.0.14.0 起；之前底數為 1.05，內丹分支同步調整）。
- L < cap 且魂魄足夠時，先扣魂魄，再將 z9 y6 增加 1，最後刷新角色。
- E3 最大升級重複同一判斷，每輪重新取當前 L 算成本；到上限或不足即停止。累計成本是逐級 C 的總和，不是只用最終等級算一次。
- 單次成本取整與最大升級資源寫入的 round 都應照原版核對；原生函式只操作 z9，z7 oracle 必須先透過原生搬入並取得目的列。

E5 的 round(10000×L^(0.2+0.1T)) 的確存在，但本次整個 project 的名字掃描只找到函式定義，沒有 [5, 函式名] 引用或直接動作呼叫。E1–E3 也沒有寶物經驗餘額寫入。因此本版**不設寶物 addExperience、不連動虛構經驗、不配置經驗輸入框**。這是當前來源的靜態結論，不能推論所有歷史／未來版本都沒有經驗系統。

編輯器建議維持既有裝備政策：直接設定合法等級、不扣資源；介面說明這不是代做原生付費升級。降低等級沒有原生降級函式可當 oracle，須與原生取得的合法低等級基準比較效果，再驗存讀及後續升級。

## 3. 穿卸與搬移

E6 穿戴從 z7 讀 wp6 部位。寶物是第 6 槽，因此角色指標為 **save[角色,21,2]**，指向 z9 列；該列 y7 反指角色。

- 空槽：先原生存入 z9，等待完成，再用實際返回列寫角色指標與 owner，刷新角色。
- 已有裝備：先將原 z9 裝備取出，再存入新件，更新指標與 owner。不能假設原列號不變。
- 卸下：原生取回 z7，等待完成，再清角色第 6 槽與目的 z7 owner，刷新角色。
- E7 逐欄複製 **y0–49**，同時清來源 y0–49；y50–59 不在該搬移迴圈中，驗證仍需監看，不能假設自動清零。
- 直接調等級不應改庫別、owner 或角色指標；已穿戴寶物必須唯一雙向一致。未穿戴 z9 不得被角色引用，z7 的相同行號也不是 z9 引用。

這些順序含 WaitForPreviousActions；未來測試須等待實際完成、核對返回列及整列資料，不能只呼叫函式後立即讀值。

## 4. 分解與返還

E8 讀 z7 的 y6、y3、y5、y8 傳給宝物价格，但該函式的「卖」分支實際**只按等階**回傳：

| 等階 | 分解魂魄 |
| --- | ---: |
| T1 | 20 |
| T2 | 200 |
| T3 | 1,000 |
| T4 | 10,000 |
| T5 | 50,000 |
| T6 | 500,000 |

等級、品質、主係數雖然作為參數傳入，在此分支未參與計價；不累加曾付出的升級魂魄，也沒有讀投入／退款帳本。提高等級不應增加分解收入，降低等級也不應減少它。

分解先呼叫获得魂魄，增加 save[3,2,0]，再呼叫失去物品清空 z7 列。刪除迴圈是 Height+1，與搬移固定 50 欄不同；應以實際有效欄全清及其餘列未變作斷言，越界行為須由原生測試觀察。

批次分解按品質、y22 非鎖定及寶物類型／第 6 槽過濾，再走同一分解函式。取得流程也有自動／滿倉分解分支。函式本體不是完整 UI 資格檢查；驗證只用合法背包寶物，穿戴中需先卸下，不能直接拿 z9 行號呼叫 z7 分解。

## 5. 實作建議與首次證明設計

候選 API：treasureLevelInfo／previewTreasureLevel／setTreasureLevel，或既有裝備入口的獨立寶物分派；名稱在實作時依現有結構決定。共用 token、transaction、undo／restore、owner 檢查的機制，但不能放寬普通裝備或套裝的 kind 判斷。

候選群組為 backpackTreasureLevel（z7）與 treasureLevel（z9），獨立首次證明；只寫 y6。一般模式 Q1–Q6、T1–T6，排除超限、內丹、生成、品質／詞條、批次升滿與代分解。原型別保留；同件累計還原沿用裝備交易分組，失敗不留部分變更。

首次驗證應包含：

1. **合法基準**：170 範本 × Q1–Q6 原生取得，記錄完整 metadata、類型及來源；無法原生產生的組合列缺口，不用人工假造補分母。
2. **等級邊界**：每個合法範本／品質在兩庫驗 1、cap−1、cap 的升降／無變更；0、cap+1、小數、錯型別、未知範本與損壞互指為拒絕案。穿戴 z9 另覆蓋第 6 槽；兩庫不能互代。
3. **效果**：以原生装备主属性／角色刷新對照，涵蓋所有寶物主屬性類型；預期不能來自被測 core。取整造成數值相同可合法，不要求每次升級都可見變大。
4. **成本**：T1–T6、各 Q 上限的單次與最大升級；魂魄不足、恰足、多級與封頂。編輯器不扣資源，原生付款側另算成本，不比較兩邊全部資源相等。
5. **生命週期**：原生存入／取出、空槽穿戴／替換／卸下、升級後再搬移；跟蹤返回列、y0–59、角色第 6 槽及 owner。每個必要階段原版存檔、停止、新 PID 讀回。
6. **分解**：各 T 升／降前後返還相同；Q1/Q6、低／高等級、不同係數基準，確認只加固定魂魄、該背包列清空、其他列不變。批次鎖定／未鎖定與品質篩選另驗，不把單件結果當批次通過。
7. **證明與 UI**：兩庫各自完整首次證明、遷移需求／suite／manifest／相依宣告；桌面／390px、精確匯出重載、直接 file、PWA 離線及更新交接。改 core 後核對既有全部群組相依，尤其技藝上限整份 AST。

矩陣是待執行設計，實際 case ID／數量由合法基準固定後寫入 manifest。完整原生 suite 可分片續跑，但缺案、來源變動、失敗與未測必須可對帳，不能縮分母後宣稱全過。

## 6. 決策與續做

- **可進實作的原因**：可寫語意收斂為單欄 y6；上限、魂魄成本、搬移與返還都有可追溯的靜態來源，並可建立獨立 oracle。
- **開放前仍須解決**：原生合法品質／metadata、兩庫存讀／重啟、穿戴效果、分解返還及取整邊界；目前全部未實測。
- **反證處理**：若原生結果顯示隱含經驗、額外寫入或退款，停止對應群組，回寫研究與規格；不套用目前單欄結論。
- **現況**：[SDD](../../sdd/archive/2026-10-23-treasure-level/tasks.md) 十項已完成，v2.11 已發布並歸檔；本節的動作清單為研究當時的規劃，不再是待辦。
