# AI 維護與開發優化方案

規劃基準：2026-11-04，`81d6370` 的編輯器漸進拆分。P1 已實作並驗證，實作摘要見文末；P2／P3 與原生工具拆分仍是後續候選。現行來源與測試入口見[來源組裝與責任分檔](../maintenance/core.md#來源組裝與責任分檔)。

## 目標與目前瓶頸

讓 AI 接到一項修改時，能從目前來源取得「實作在哪裡、哪些地方會受影響、要讀哪份規則、應選哪些驗證」，並能及早發現越過公開介面或漏登記的改動。

- 核心雖拆成 12 個片段，仍共用封閉作用域。初步具名呼叫掃描找到 197 個頂層宣告；技藝／天賦會呼叫其他 5 個片段，資質／結丹及裝備／交易／序列化各有互相呼叫的群組。這是導覽線索，不是完整 JavaScript 呼叫圖，也不代表這些相依本身有錯。
- 目前有 61 個寫入旗標、12 個 migration family；family、證明 section、公開方法根集合分散在既有登記表。它們有不同語意，後續整理應保留共享及多對多關係。
- `SaveCore` 有 101 個公開名稱，完整契約仍分散在原始碼、維護文件與測試。AI 目前需要交叉搜尋才能理解預覽身分、失效條件及累計還原。
- 圖譜是跨文件研究的輔助入口；本次拆分後已標記待更新。日常程式定位需要可直接讀目前來源、無須先做語意萃取的工具。

## 優先順序

| 順序 | 工作 | 預期收益 | 範圍 |
| --- | --- | --- | --- |
| P1，已完成 | 即時程式導覽、相依檢查及驗證建議 | AI 能自行查到修改位置、影響與檢查入口，確定的錯誤有明確診斷 | 工具、測試、技能與文件；保留產品行為 |
| P2 | 補公開介面的 JSDoc 契約 | 減少誤解 options、回傳值、預覽與交易規則 | 先以技藝上限及交易介面為樣板，再擴充 |

P1 先補足可觀察性及檢查能力，再據此選擇封裝位置。原有單檔 HTML、共用作用域、寫入旗標與證明演算法繼續沿用。

## P1 實作方案

### 1. 共用組裝入口提供來源位置

在 `scripts/editor-source.cjs` 增加 `readEditorSourceDetails(entry, {root})`，回傳 `{source, segments}`；原有 `readEditorSource` 回傳相同的程式字串，並共用這個組裝流程。

`segments` 記錄每段的 `file`、`sourceStart`、`outputStart`、`length`。偏移採 JavaScript 字串的 UTF-16 索引，顯示行號從 1 起算；可將組裝後 AST 的位置映回片段原檔。來源索引在注入 catalog 前建立。凍結版本的完整單檔核心對應原檔，不混入現在的片段。

來源清單仍只有一份，組裝標記、順序與錯誤檢查沿用現有規則。每次查詢讀取目前來源，先不提交會過期的索引產物，也不加入執行期依賴。

### 2. 加入 AI 可直接使用的查詢工具

新增分析模組與薄 CLI，使用已附帶的 Acorn、來源位置及既有 verification／migration 登記表。提供以下入口：

```sh
npm run inspect:editor -- --symbol setCharacterSkillCaps
npm run --silent inspect:editor -- --family randomCharacterSkillCaps --json
npm run inspect:editor -- --group randomCharacterSkillCapsAdvanced
npm run inspect:editor -- --file src/core/skill-caps-talents.js
npm run inspect:editor -- --changed --base HEAD
npm run --silent inspect:editor -- --changed --staged --json
```

單一查詢選擇 symbol、family、group 或 file 其中一種；`--changed` 為另一種模式，預設比較 HEAD 與目前工作內容，包含未追蹤來源。`--base` 與 `--staged` 互斥。錯誤名稱或無效參數明確失敗，`--help` 列出使用方式。

一般輸出與 JSON 提供定義位置、直接相依／被引用位置、公開匯出、family、旗標、證明 section、靜態可找到的測試候選，以及既有功能／測試指引入口。JSON 至少包含 `definitions`、`dependencies`、`dependents`、`families`、`groups`、`suggestedChecks`、`limitations`。

分析區分宣告與作用域，排除同名區域變數、非計算式屬性名稱及註解造成的假相依。動態方法選取、間接別名或未支援語法明示限制，不能宣稱已找到所有呼叫者。family／section／旗標讀既有登記表，不另維護一份功能開放清單；研究入口繼續由既有功能導覽提供。

### 3. 加入確定性架構檢查

提供 `npm run verify:architecture`，檢查目前組裝入口、來源相依與公開介面，確定的違規以非零結束並指出原檔行號：

- 組裝後頂層宣告的擁有位置明確，公開匯出的實作可解析。
- UI 明確使用的 `SaveCore`／`C` 方法存在於公開匯出；動態選取另列人工核對項。
- 核心維持無 DOM、網路與 Node I/O 的責任；依作用域辨認實際環境名稱，不以文字搜尋判斷。
- 既有旗標、family、需求 section 與 core roots 的關係可解釋；沿用合法的共享與歷史命名，不強制一對一對應。

現有循環及動態呼叫先列成診斷資訊，不把圖譜中的邊或檔案大小直接當成錯誤。純度規則先約束核心；目前 UI 與原生工具仍保留各自環境能力。

### 4. 輸出保守的驗證建議

`--changed` 僅列出建議及原因，不自動執行測試、遊戲或發布。`--staged` 使用 index 的 Git bytes，沿用暫存快照方式讀取，並使用快照內對應版本的組裝規則；無法取得相符規則時明示限制並保守回退。一般模式讀目前工作內容。

- 具名功能變更：列出相依可追到的 family 與測試候選，標示為靜態候選。
- 共用座標、欄位權限、交易、序列化或組裝流程變更：建議完整 Node 與相應瀏覽器回歸。
- 純文件變更：建議連結、規則一致性與差異檢查。
- 刪除符號、新檔未登記、動態相依或無法定位測試：明示覆蓋不完整，回退至完整 Node；涉及產品來源時再列完整瀏覽器，不輸出「無需測試」。

推薦命令沿用現有測試入口；原生冒煙仍由新寫入、讀寫行為變動或遊戲版更規則決定。這份建議不取代[輕量流程](../maintenance/lightweight.md)或[待提交快照檢查](../maintenance/release.md#待提交快照檢查)。

## 驗證與完成條件

- 用小型合成程式驗證同名區域變數、函式／箭頭函式、計算式屬性、匯出別名、跨片段呼叫、動態呼叫與循環；中文來源及多行模板的位置必須映回正確原檔。
- 以目前技藝上限查詢驗證公開方法、實作位置、一般／進階旗標及 family 關係。檢查錯誤匯出、UI 拼錯方法、核心使用環境 I/O、缺失登記等反例能給出明確診斷。
- 在暫存 repo 驗證未暫存、已暫存、未追蹤、刪除及純文件變更；`--staged` 不受同一路徑未暫存內容影響，未知影響會啟用保守回退。
- 組裝後 core／UI 文字、AST、公開匯出與 family 切片維持實作前基準；既有組裝、切片與建置閘門測試通過，`build-editor.cjs --check` 通過。產品來源或產物確實改動時，再跑對應網頁回歸。
- 技能提供「接功能先查工具，再讀命中的規則」入口；AGENTS.md 維持精簡路由。Graphify 繼續負責跨文件研究，來源位置與靜態檢查以目前原始碼為準。

完成標準是：新開工作階段可由一個符號、旗標或變更檔案取得可核對的維護線索；資訊不足時會清楚說明，並提供完整驗證的回退方式。P1 完成後，再另行具體規劃 P2／P3，不一次重寫全部介面與驗證框架。
