# v2.3 精準洗練：原版效果公式研究

研究日期：2026-10-21；來源為 V1.0.10.2／Steam build 26094666 的 `data.json`、`scripts/c3runtime.js`、`wp.json` 與 `sx.json`。使用 `inspectGame` 解析事件及 expression factories；原始抽取內容留在 repo 外。本節是靜態結論，**不是新增寫入的遊戲實測證明**；開放範圍仍需獨立 verification。

## 可直接實作的結論

全部 38 個普通裝備合法隨機詞條皆有確定的純數值公式，`sx[id,4]` 全為「百分比」。可以預定涵蓋全部 38 個，但每件裝備仍須套用自己的合法池，不能直接展示全域集合。數值單位為百分點：結果 2.75 顯示為 +2.75%，不再乘 100；差異亦為百分點。

**重要修正：副詞條不隨裝備等級成長。** `装备主属性` SID `773239288013696` 的副詞條前置分支 SID `712721902672178` 先將「装备等级」強制設為 0、設定係數設為 100（expressions 5294、23、3）。舊研究列出的含 L 通式必須先套用這個前置分支，不能把存檔 L 直接帶入副詞條公式。

令 T 為 `[i,3,9]` 等階、L 為 `[i,6,9]` 等級、C 為該槽係數；保留原式浮點運算次序及 `Math.floor`，不可用顯示格式的 round 代替。

| --- | --- | --- | --- |
| 12、51 | `floor(((2+T*0.75)*(C/100))*100)/100` | `floor((((2+T*0.75)+L*0.01)*(C/100))*100)/100` | 5299／689544018455901 |

## 單件裝備效果與原生比對

`装备属性计算` SID `131416746119248` 對每件穿戴裝備：先掃三個主屬性，再掃六個詞條槽，命中目標 ID 時逐筆加到計數；最後 SID `573912943040867` 直接回傳計數，**沒有總和後再 floor**。因此既有重複詞條必須各自計算再累加，不能先合併係數再取整。

主屬性 ID 取 `wp[template,8..10]`，主屬性設定係數取 `wp[template,11..13]`；y8 是主屬性品質係數，並非 ID。主屬性與隨機詞條可重疊，例如範本 16 主屬性含 12、範本 13 含 72。預覽舊／新詞條 ID 的裝備總效果時必須保留這些主屬性貢獻。上述 38 個 ID 的主屬性公式不使用設定係數，但生成資料可保留它以忠實對應原生呼叫。來源：expressions 5355／5356，主屬性累加 SID `350164573210161`；副詞條 expressions 5357／5358、SID `970127749406416`。

原生事件函式參數順序：

```js
call('装备主属性', L, T, attributeId, coefficient, settingCoefficient, type, 0, Q)
```

- 主屬性：`coefficient=y8`、`settingCoefficient=wp[template,11+index]`、`type='主属性'`。
- 副詞條：`coefficient=save[i,15+index,9]`、`settingCoefficient=100`、`type='副词条'`；L 可照傳存檔值，原生內部會設為 0。
- 單件 oracle：依原生順序，三個主屬性與六槽命中 ID 的呼叫結果相加。不要將完整角色公式當作單件結果。
- 額外整合核對：隔離角色只穿目標普通裝備且沒有套裝時，`call('装备属性计算',characterId,attributeId,0,0,0,0,0,0,0)` 應與單件計算一致；卸下後為 0，再穿回恢復。對既有其他裝備保留者則比較整體差值。

`call` 沿用驗證工具的 `GetFunctionBlockByName`／`RunAsExpressionFunctionCall` 包裝；所有呼叫及實體準備僅限 repo 外隔離測試副本。不能為了使單件結果相符而修改正式角色穿戴。

## 品質係數、合法池與持久欄位

`装备主属性系数` SID `360141429177377`（5278–5280）生成 y8：整數外包範圍 `80+(Q-1)*30` 至 `80+Q*30`。這是生成範圍，並不表示編輯器可以更改 y8，也不能推斷任意歷史升品存檔的 y8 一定在目前 Q 範圍；超出實測範圍應停用新功能並保留原文。若要求新預覽只接受這個原生範圍，須明示限制而不是自動修正。

`装备随机词条编号` SID `557896778643212` 要求 `sx[id,8]=1`，再以 `wp[template,23]` 與 `sx[id,13]` 過濾戰鬥／生產／通用；通用裝備另排除 `sx[id,13+wp[template,9]-39]=1`。這個動態排除已由既有生成器 `batch2Data.items[].affixIds` 建立，介面應共用該資料。原生隨機函式沒有目前槽 ID 參數，不能據此宣稱重複詞條實測成功；編輯器按計畫禁止新增與其他槽相同 ID，但保留現有重複，允許保持原 ID 的無變更或合法係數調整。

係數原生外包範圍仍為 `10*(Q-1)..60+10*Q`、兩位小數（`装备词条系数` SID `631300007252337`，5287–5289）。替換操作只寫選定槽的 ID 與係數。`词条洗练` SID `619743323262026`／寫入子事件 `564254928232839` 可作後續原生洗練驗證；直接呼叫函式不等於通過 UI 選槽條件，編輯器仍要求唯一已選槽。

y23 不參與上述普通裝備的單件數值公式。`获得物品` SID `601593514747018`、普通分支 `166680919655131` 把取得品質寫 y23，但 `套装合成` SID `835824606167319` 另有靈物語意。不得隨 y5 或詞條修改同步 y23；y8、y23、品質、等級、所有旗標與歸屬一律保留。

- 38 個合法 ID 各有原生函式對照；涵蓋 T1／T9、Q2／Q6 係數上下端與取整邊界。主屬性另涵蓋 L1 與品質允許上限，特別對照 12 與 71 的不同 L 係數。
- 戰鬥、生產、通用池逐一確認；通用池測動態排除。Q2–6、不同已選槽、裝備庫及穿戴都需要完整載入／原版存檔／停止／新程序重啟。
- 主屬性與替換前後 ID 重疊、既有其他槽重複、原 ID 無變更、係數改變但取整效果相同均需測試。
- 原生同槽再次洗練後核對成本、合法池與唯一旗標；卸下／穿回、重啟後核對裝備效果及未修改原始存檔雜湊。
- 所有新開放候選須與本版來源、公式資料雜湊及實測覆蓋一致；靜態可算的 38 個集合不是自動開閘授權。

## 原生洗練成本與搬移生命週期補充

`词条洗练魂魄(等阶,已洗数)` SID `613174227852589` 在本版直接回傳常數 **100**（expression 23）。呼叫端仍傳入等階及 `装备已洗词条数(itemId,z,0)`，但函式目前不使用這兩個參數。`词条洗练(itemId,slot,z)` 的 SID `564254928232839` 先比對魂魄足夠，再呼叫 `失去魂魄(cost,false)`，然後只改目標物品的 `y8+slot`、`y14+slot`、`y27+slot`。測試可讀取 `[3,2,0]`（須按現有資源編碼處理）並核對扣 100；不要以隨機後 ID 或係數必定不同作為成功條件。

後續 SID `338766607025535` 對 z9 呼叫 `刷新单角色单属性(owner,newAttributeId)`，未在此函式看見同時刷新舊 ID 快取。測試須分開記錄原生公式讀值與即時衍生快取，不應先額外呼叫全刷新來隱藏這個原生行為；重新穿戴及重啟後另核對舊效果已移除。

原生呼叫：

```js
call('卸下装备', actualSlot, equippedItemId, characterId, false, false);
call('穿戴装备', actualSlot, bagItemId, characterId, false, false);
```

- `卸下装备` SID `501272375624196`：取得角色 `[characterId,15+actualSlot,2]` 的 z9序號，呼叫 `装备库取出`；將角色該指標歸零，將返回的 z7 物品 y7 歸零。實際槽位不可固定為 1。
- `装备库取出` SID `654692930556623`／搬移事件 `418018161514165`：尋找 z7 的空列（y1<=0），將 z9 的 **y0..49 共50欄** 複製至 z7，同時把源 z9 這50欄清零。範圍來自 repeat 常數 expression53=50及從0起始的計數。
- `穿戴装备` SID `924571110308816`：會由 `wp[save[bagItemId,1,7],6]` 重新取得 actualSlot（expression2859），若有原裝備先取出，再呼叫 `装备库存入`。設定角色 y15+slot 為新 z9序號及該裝備 z9 y7 為角色序號，刷新角色全屬性。
- `装备库存入` SID `791657421740250`／搬移事件 `959041203712077`：反向複製 y0..49 至首個空 z9列，清空源 z7的50欄。

搬移函式靜態上連 y0 也直接複製，不能假設搬移後仍占相同列號，或預設所有識別欄都由搬移重編。驗證應追蹤角色指標、原生返回序號與目標模板／詞條識別；比較詞條、品質、等級、y8、y23、旗標等有效負載，另核對owner變更與源清空。z2/z12角色衍生數值及引導任務亦可能因刷新改變；不能要求完整存檔只有目標50欄改變。

對新增核心的獨立靜態複核：`affixEffect`、`equipmentAffixEffect` 的 L 規則、主屬性重疊及逐槽加總與上述原式一致。`setEquipmentAffix` 以同一交易改 ID／係數，既有重複保留、新重複阻擋及無變更不寫入均符合計畫。y8原生生成整數；若預覽仍允許兩位小數的歷史y8，需另納原生比對案例或縮限為安全整數，不能只以合法區間宣稱生成格式相符。

### 搬移識別修正

實測裝備從 z9 列 1000 搬回列 41，y0 仍為 1000。`获得物品` 普通分支 SID `166680919655131`、action `581082896161345` 建立 y0 初始背包列號；原生搬移複製該值，背包列重用也可能產生相同 y0。原先要求 y0 等於目前列號會誤拒合法裝備，現共用檢查改為正安全整數且小於陣列 x 尺寸，保留範本與穿戴雙向關聯檢查，絕不改 y0。另補合成測試涵蓋不同列號、重複 y0 與非法邊界。

### 證據與測試工具限制

去識別證明寫入 `knowledge/verification.json` 的獨立 `equipmentAffixReplacement`，含完整 15 來源、規則／資料雜湊、限制、38 候選及通過項目。原始 scenario、state、輸出與玩家資料僅留 repo 外；`v23-results.json` 彙整五組結果，後續生命週期及搬移再編輯另有紀錄。

測試工具初次用 SDK 讀 wp 時漏傳 z=0，修正後重跑；卸穿事件有延後動作，初次即讀誤判失敗，改為等待事件完成再核對並從未修改的隔離存檔重跑。Q4 停止時遇到子程序先結束的競態，確認舊程序已消失後才啟動新 PID 完成驗證。這些是工具修正，不作為遊戲失敗或略過測試的理由。

效果證據來自原生 `装备主属性` 與 `装备属性计算`、卸穿及重啟讀回。未額外全刷新掩蓋原生洗練只刷新新 ID 的快取行為；未宣稱完整角色面板或其即時 UI 快取已驗收。

## v2.3 瀏覽器驗收

本機 HTTP 桌面與 390px 通過合法池搜尋、預覽、非法三位小數阻擋、套用、整件還原、復原一步，以及主介面／變更視窗兩個匯出入口。390px 文件寬度為 390，沒有水平溢出。四份實際下載檔與核心序列化輸出逐字相同，保留 BOM、CRLF 與超過安全整數的原文。
