# 套裝品質 go／no-go 研究

> 現況（2026-10-25）：本研究的套裝品質已依 [A／B SDD](../../sdd/set-equipment-quality/tasks.md) 完成並作為 [v2.12](../releases.md#v212-套裝品質) 發布；下文的 go／no-go、「下一個候選」與待核准敘述是 2026-10-23 研究當時的狀態。

研究日期：2026-10-23。編輯器基準 v2.10，遊戲 **V1.0.11.2／Steam build 26126719**。本輪只有 repo 與既有本機來源快取的唯讀分析；未啟動遊戲，未修改 src、catalog 或 verification。本文件是研究結論，不是已核准的 SDD 或首次寫入證明。

**結論：有條件 go，適合作為下一個功能進入 SDD；目前開放套裝品質寫入仍為 no-go。** 範圍須包含合成繼承池與原生洗練池的區分，以及套裝等級資格檢查的相容性驗證。若只把普通品質的套裝排除移除，或只沿用 y27 原裝備詞條池，則為 no-go（Q3、Q4、Q8；詳見末節）。

## 1. 目前進度與來源界線

[目前進度](next-version-plan.md)與[路線圖](feature-roadmap.md)記錄 v2.9 天賦、v2.10 套裝等級已交付；[套裝等級 SDD](../../sdd/archive/2026-10-23-set-equipment-level/tasks.md)已歸檔。路線圖第 3 項的套裝等級前置已完成，第 5 項的套裝品質／詞條仍待評估。歷史排序不代表現在必須先完成寶物；本研究建議先處理既有套裝品質，不一併開放任意詞條替換、係數編輯、積分、生成、重複合成或超限。

靜態核對目前 `equipmentQualityInfo` 仍先呼叫 `ordinaryEquipment`，不接受套裝；`setEquipmentLevelInfo` 是另一條只開等級的路徑。既有普通品質四群組與套裝等級兩群組不能代替新品質證明。這是 repo 狀態，沒有對應遊戲 SID；相關遊戲語意見 Q1–Q9。

本輪依 `.local/game-sources.json` 的 `preferredDevelopmentSourceId` 沿用完整快取，核對來源 manifest **274 檔**、runtime manifest **18 檔**的 SHA-256，全部相符；15 個分析來源也與目前 catalog 的主／補充指紋相符。runtime 僅讀檔核對，沒有執行；未重解包、未重新掃描安裝版本。關鍵來源摘要：

## 3. 可封閉的品質交易

**靜態核對：** Q1 的主係數為 `80+30(Q−1)..80+30Q`、副係數為 `10(Q−1)..60+10Q`，槽數是 `clamp(Q,1,6)−1`。Q2 上限是 `10+5(Q−1)`。只接受 Q1–Q6 時可推得下列確定性變換；「保留 roll 平移」是編輯器政策，不是已找到原生升／降品質按鈕：

- y5 改成目標品質；y8 加 `30×ΔQ`；保留槽係數加 `10×ΔQ`，以百分之一整數運算避免浮點誤差（Q1）。
- 升品明選每個新增連續尾槽的 ID／係數；旗標保持 0。降品清除移除槽的 ID／係數／旗標並要求確認；移除已選槽則拒絕，不重選槽（Q1、Q4；沿用普通品質產品政策）。
- y6 保持；若高於目標 cap，先拒絕，另由已開放套裝等級功能降低，不在品質交易偷改等級（Q2）。
- 保留 y0、y1、y2、y3、y7、y23、y24、y25、y26、y27 及其餘非交易欄；保留既有重複詞條但不新增重複，無變更不建立交易。非法輸入原子回滾、跨品質／等級整件還原與 undo 須另驗（Q3、Q8、Q9；交易行為為建議）。

**靜態核對：y23 不等於目前品質。** 合成以靈物 z18 y4 寫入 y23，以 z18 y10 寫入 y26，y27 保存原範本；不能隨 y5 同步（Q3）。保持範本、穿戴組合與這些 metadata 時，額外套裝加成的 S／N／啟用部位數應保持，單件效果則會因係數、槽數與攻擊 L×Q 改變（Q5–Q7）。y26 的完整下游用途仍未知，不能把「合成來源已定位」寫成完整語意已證明。（後續 2026-10-25：固定座標與動態 y 讀取都查不到 y26 的讀取者，原生合成也確認把靈物 y10 原樣寫入，見[靈物合成與精煉驗證](candidate-sweep-2026-10-23.md#原生驗證摘要2026-10-25修改後靈物用於套裝合成與內丹精煉)。）

**未知：** 人工品質變更後，載入、刷新、洗練、原版存檔與新 PID 讀回是否保持上述結果。本輪沒有新原生證據；既有品質或只改 y6 的證明都不能補足（Q1–Q9）。

## 4. 關鍵差異：繼承池與洗練池

**靜態核對：兩池不能視為相同。** 合成不重抽既有槽，因此繼承槽來自 y27 普通範本；後續原生洗練 expression 4866 明確傳入 `save.At(row,1,plane)`，再由 2390 讀當前範本 wp23（Q3、Q4）。本版 wp 表有 216 套裝，戰鬥／生產池各 108；243 普通範本的通用／戰鬥／生產池各 81。例如 T1 武器「土匪之槍」#28 是戰鬥池，同階同部位普通武器 #1–9 是通用池。這些是本版資料表統計，不是原生抽樣結果。

**建議首版政策：**

| 槽狀態 | 候選資格／新增規則 | 理由與待驗 |
| --- | --- | --- |
| 既有未選槽 | 依 y27 原範本池核對 | 合成繼承；不能因 ID 不在套裝池就判非法（Q3） |
| 既有唯一已選槽 | 原範本池或目前套裝池，保留旗標；不得擴大其他槽 | 旗標不能單憑一個 bit 還原所有歷史；需原生首次選槽／洗練前後見證，不能宣稱完整來源可由存檔證明（Q3、Q4） |
| 升品新增尾槽 | 明選 y27 原範本池、目標品質係數，旗標 0 | 採「目標品質普通裝備取得後再合成」可達狀態作為設計依據；不是任意替換既有槽。須先取得原生生成見證（Q1、Q3） |
| 後續遊戲洗練 | 由原生目前套裝池產生 ID，核對目標 Q 的係數 | 不要求洗完仍屬原池，也不控制隨機結果去迎合編輯器（Q4） |

**已發現的 repo 風險：** 現行 `setEquipmentLevelInfo` 對所有有效槽都要求 `origin.affixIds.includes(id)`，沒有已選槽的套裝池分支。因此原生洗練若產生套裝池專有 ID，等級 helper 可能拒絕該件；這是由目前程式與 Q4 得出的靜態推論，尚未實跑重現。套裝品質 SDD 必須納入共同資格檢查與等級回歸，不能只在品質 API 放寬，也不能改成全部槽無條件取兩池聯集。

如無法以原生見證封閉這個政策，應縮限明示支援範圍或回到 no-go，不得把合法但尚未支援的列說成損壞存檔。重複套裝合成、來源 metadata 缺失、特殊主係數及超限保持另案（Q1、Q3、Q4）。

| 面向 | 本輪判斷與依據 |
| --- | --- |
| 價值 | 補完目前套裝只能改等級的常用操作；屬產品判斷，沒有使用量調查。品質會實際影響槽數與單件效果（Q1、Q5） |
| 可重用部分 | 普通品質已有平移／刪槽／整件交易；v2.10 已有 tz、216 範本、原生合成基準、獨立效果與搬移工具。可重用工具結構，不能複製首次證明（Q3、Q5–Q9） |

| 相對順序 | v2.10 已降低套裝 metadata 與效果研究成本，可優先接續品質；沒有重新完整調查寶物／丹藥，故不宣稱品質絕對最便宜。歷史第 5 項與當前前置已不同 |

[套裝等級研究的 B 紀錄](set-equipment-level.md)已有 1,944 份取得／合成基準與 12 份生命週期結果，可作待核對的輸入來源。它們沒有證明改品質後新增／刪除槽或跨池洗練；不能把該案 15,552 等級案例計入本案品質通過數（Q1、Q3、Q4）。

## 6. go 後必須寫入 SDD 的條件

以下是**待核准、待執行的驗證設計**，本輪未新增群組、腳本、旗標或證明。

### 四個獨立群組

建議名稱為 `backpackSetEquipmentQualityUpgrade`、`backpackSetEquipmentQualityDowngrade`、`setEquipmentQualityUpgrade`、`setEquipmentQualityDowngrade`。z7／z9 與升／降各自保存首次證明；Q 相同為無操作。首版僅既有原生普通→套裝、Q1–Q6、T1–T9、數量 1、合法等級、完整 metadata、無特殊狀態及有效互指的列。z7 owner=0；z9 分未穿戴與穿戴；y0 不要求等於列號（Q1–Q4、Q8、Q9）。

新增需求表、suite、情境、oracle、proof 與相依摘要，來源綁全部 15 指紋、實際規則／資料及被測程式。首次證明前四群組各自關閉；代表遷移不能補首次。若改 core，依[目前進度](next-version-plan.md)與[遷移維護](../maintenance/migration.md)處理技藝上限、套裝等級等受影響既有證明。這些為 repo 開發規則，非遊戲 SID 結論。

### 獨立 oracle

1. **交易 oracle：** 獨立推導 Q1 區間平移、Q2 cap、槽數增刪及第 4 節池政策；比對指定 token，保留其他原文、BOM、大型整數、型別與 metadata。預覽不能作自己的答案；錯誤輸入須完全不變。
2. **生成可達性 oracle：** 用相符來源的原生「特定装备」取得明確 Q/T/主係數，再依合法 recipe／靈物合成，分別見證起點與目標品質的結構。原生生成槽可能隨機，不能假定同一 seed 或強制相同 ID；明選候選逐池核對，數值結果另由效果 oracle 驗證（Q1、Q3、Q4）。未找到可充當確定性升／降品真值的原生操作，不虛構「原生升品比對」。
3. **效果 oracle：** 以目前套裝 y1 的主屬性設定及各槽，獨立計算全部受影響屬性，與原生 `装备属性计算`、刷新後角色屬性比對；攻擊 L×Q、百分比取整、主副重疊、移除舊效果均納入。另核對 S／N／部位數／額外套裝效果不因品質交易變動（Q5–Q7）。
4. **生命週期 oracle：** 品質變更後載入、刷新、原版存檔、停止與新 PID 讀回；原生同槽洗練後核對套裝池、係數／旗標及實際成本，重新由品質與等級資格 API 檢查，再完成搬移、穿卸及第二輪 IO。目的列由實際搬移結果識別，監看 y0–59；原生 IO 允許已核對的副作用，不要求全存檔 byte 相同（Q4、Q8、Q9）。洗練刷新傳入新詞條 ID，因此必須另比對完整效果與舊屬性移除；洗練頁的槽數／停用狀態仍需獨立 UI 驗收（Q10）。
