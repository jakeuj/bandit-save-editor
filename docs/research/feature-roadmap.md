## 排序方法

每項以五個面向評估：玩家價值、靜態寫入點與關聯規模、新增隔離驗證成本、可重用的既有核心與驗證工具，以及每次遊戲改版的重驗負擔。排序採平衡原則，玩家價值高、又能重用既有裝備／經驗交易的項目優先。寫入點很少但語意是衍生值、或牽動地圖與實體生命週期的項目延後。

遊戲更新頻繁。依目前建置規則，事件或資料表指紋變更後，需重新核對受影響的寫入群組，不能沿用舊來源證明。新增群組須首次獨立證明；後續按相依摘要沿用或選跑，詳見[精簡流程](selective-migration.md)，成本仍須計入排序。

## 各項說明

### 0. 版本遷移重驗流水線

原有驗證分散於 `verify-game.cjs`、`verify-advanced.cjs`、`verify-batch2.cjs`、`verify-affixes.cjs`、`verify-affix-lifecycle.cjs`、`verify-equipment-workflow.cjs`、`verify-quality.cjs` 與 `verify-quality-lifecycle.cjs`，各自有 repo 外的 scenario 與 state。V1.0.10.2 遷移時只需重驗名稱與經驗；後續來源異動須按當時已開放群組重新驗證，其中品質就有 800 件寫入與 6,592 組公式比對。

建議把各群組的代表 scenario 整理成一份 repo 外清單，由單一入口依序完成隔離載入、原生存檔、停止、新 PID 重啟及 assert，再輸出逐群組的去識別結果供人工審核後寫入 verification。這不改變「完整指紋相符才開閘門」的規則，也不把舊證明套到新版。

以下為A階段靜態來源；B階段新增實測範圍另依上述紀錄：

- `数值更新` SID `907064845535449` 的回填子事件 `501010543923483` 有三個條件：迴圈索引大於 0、`save[r,0,2]>0`，以及 `save[r,2,2]>0`。也就是只有角色範本大於 0 的有名角色會被 `js` 範本覆寫 y10–12、y22–30 與 z12 的 y1–3／21–23。
- 將低於範本初值的技藝等級補高的 `429172563476993`，是上述子事件的子事件，同樣只作用於有名角色。
- 這些欄位的其他寫入點為招募（例如 `招募随机角色` SID `909963012425650`、`564152387768918`，天賦 `834941377542149`、`589480535668937`）、收監及解雇初始化。`角色重生`（含子事件 `659056119211235`）在 z2 只寫 y3、4、13–15、50、56，不碰基礎資質。

因此範本0一般隨機角色的這三類欄位，有機會用存檔修改並持續保存。[補丁提案](../../sdd/runtime-patch/proposal.md)的回填前提只適用於有名角色。

建議順序為基礎資質、技藝上限、天賦。開工前須查清：

- 原版招募的資質生成範圍，作為一般模式值域；超出範圍歸入第 9 項超限。
- 資質上限 `C=round(100×A×M)/100` 與倍率 M 的結丹相依，詳見[第二批研究](advanced-editing-batch2.md#三丹藥資質增量)。下調基礎資質後，既有丹藥增量 B 可能超出新上限，須阻擋或明確處理。首輪比照丹藥，只支援無結丹紀錄的角色。
- 技藝上限與現有等級、達上限後餘額清零的時序；B正式隔離suite已確認差一步加10剛達上限留下9、下一次已封頂呼叫清零。不存在第 10 項技藝。
- 天賦須在 `tf` 合法池內，並核對 `天赋属性计算` SID `778369382997146` 的解讀。

驗證建議分成三個獨立群組，各自涵蓋載入、原生存檔、新 PID 重啟，以及後續服藥、重生、轉職與再次載入時沒有被回填。有名角色必須在介面明確停用並說明原因。

## 歷史：V1.0.11.0 對既有群組的影響

依 2026-10-21 測試分支公告，正式化時須注意：

- 新增保存自動召喚與自動挑戰狀態，存檔欄位與事件會變；來源指紋變更後，既有群組不能沿用舊證明，需用第 0 項流程重驗。

- 套裝合成可直接選取角色裝備，影響第 5 項及 z9 歸屬驗證。

以上為測試分支時的歷史待辦；V1.0.11.2 已完成正式對齊、隔離存讀與必要 UI 補測，見[當次紀錄](v1.0.11.2-audit.md)。後續更新先依[維護指引](../maintenance/core.md#重建知識與開放寫入)以 `--audit-only` 取得 repo 外 audit，再依 SID 比對上述事件。
