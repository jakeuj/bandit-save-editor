## 1. 套裝是否共用品質等級上限

**靜態核對：是。** E1 的上限函式只有品質參數，回傳 `10 + (Q−1)×5`；Q1–Q6 對應 10、15、20、25、30、35。升級事件先區分寶物／內丹與其他裝備，套裝落在後者，仍以 z9 y5 呼叫上限，不另取 `tz` 或套裝積分。不能從函式可接受其他數字推導 Q7 或超限合法。

**未知：** 套裝在遊戲載入後是否保留人工降級／升級結果、原生刷新與存讀是否符合預期，未驗證（E1、E2、E6）。首版建議只接受既有套裝、Q1–Q6、範本等階 T1–T9、`1≤L≤上限`，不連帶修改品質或建立套裝。

## 2. 升級分支與成本

**靜態核對：兩個升級函式直接處理 z9。** 單次與最大升級在套裝分支都只把目標 y6 加 1，並扣銅錢、刷新角色；最大升級逐次檢查餘額與上限，不能直接以最後一級成本代表總成本（E1、E2）。本輪沒找到這兩個函式直接寫 z7 y6 的路徑；背包驗證需經 E8 原生搬入 z9 後比較，不能把 z9 函式用相同列號當成背包 oracle。

**靜態核對：套裝原生升級使用銅錢。** 以升級前等級 L、等階 T 計：

- 銅錢難度 `D=(T−1)×30+L`；成本為 `round(0.05×B(D))`，其中 `B(D)=ceil(150×D^1.7×1.009^D/100)×100`（E3：5319、5320、5464）。不能套用魂魄的指數公式。
- 魂魄函式也有非寶物的計算分支：難度 `D魂=(T×6/9−1)×30+4L`，成本 `round(10×1.05^D魂−1)`；寶物分支改為 `(T−1)×30+4L`（E3：5322–5324）。但在 E1／E2 的實際呼叫分流，套裝進銅錢分支，寶物／內丹進魂魄分支。**函式能算出套裝參數的魂魄成本，不代表套裝升級會扣魂魄。**

**未知：** 尚未原生比對餘額剛好／不足、最大升級的累計扣款與封頂後無變更（E2、E3）。未來編輯器等級修改可維持既有不扣資源政策；oracle 的原生升級側必須另核對扣款，不能要求兩側資源完全相同。

## 3. y6 與套裝加成、y23／y26／y27

**靜態核對：單件主屬性與詞條會讀 y6；套裝加成本身不讀 y6。** E6 的 5367／5369 將穿戴裝備的 y6 傳給 `装备主属性`。套裝分支則由 5370 取得激活部位數、5371 取得積分、5372 取得相同套裝件數，再由 5374／5376／5378 計算並分攤加成。因此改等級可改單件效果，不能宣稱套裝積分也會提高。

**靜態核對：** E4 先比 `wp[template,16]` 的套裝 ID，再按 `wp[template,17]` 分部位，讀穿戴 z9 y23；每部位保留較大的值。首次部位計數條件有反轉旗標，例如 SID 944863480488013 是「不是已大於 0」，不能只按扁平 expression 誤讀。模式 0 回傳部位數、模式 1–6 回傳部位值、模式 9 回傳六部位值總和 S（3038）。E5 計算相同套裝實際穿戴件數 N，E6 呼叫側將 N clamp 至 1–6，避免直接按部位數分攤。

**靜態核對：** E6 的 `套装属性(attribute, coefficient, S)` 依 `sx[attribute,4]` 分三支：百分比 `coefficient/40×max(S,4)`（5329）；倍率 `round(coefficient/4×max(S,4))/1000`（5330）；整數 `coefficient/5×max(S,4)`（5332）。角色計算在部位數達 2／4／6 時讀 `tz` 欄 3/4、5/6、7/8 的屬性／係數，逐件加上該效果除以 N 的值（5373–5378）。這是來源公式核對，沒有數值實跑。

| --- | --- | --- |
| y23 | 合成寫入所用靈物 z18 y4（E7：3569）；穿戴套裝積分來源（E4：3037） | 保留原值，不能改成目前品質或新等級。合法生成值域仍需原生基準證明 |

| y27 | 合成先存原裝備範本 ID，再替換 y1（E7：2753、15，動作有順序） | 保留原範本 ID，不能清零。重複合成等後續操作的完整語意尚未證明 |

**靜態推論：只改等級不需同步改這三欄。** E2 的等級直接寫入沒有觸碰它們；E4–E7 也沒有以新 y6 更新它們的相依。這不是全遊戲生命週期的不變證明。首次驗證仍須觀察載入／刷新／原生升級／存檔／重啟，以及合成來源 metadata 是否保存；不得沿用普通裝備「y26／y27 必須為 0」的資格檢查。

## 4. tz 列資料與基準條件

**靜態核對：catalog 缺少可供套裝公式使用的 tz 列資料。** `scripts/extract-game.cjs` 目前只放 `tz.json` 到 `batch2Fingerprints`，`batch2Data` 只有 items／characters／talents／pills。原表尺寸 55×19×1，扣 header 共 54 組；`wp` 有 216 件套裝，涵蓋 T1–T9，54 個 setLink，部位 1–4。54 組 `tz` 的件數欄 2 均為 4，六件效果欄 7 均為 0；首版不可捏造自然六件效果情境。資料語意依據為 E4、E6 的 `wp16/17` 與 `tz3–8` 讀取。

**建議：要納入最小 tz 列資料與規則摘要。** 至少需 set ID、名稱、欄 2、三組效果 ID／係數（3–8）及成員範本（9–14）；另納入 `wp` 的 setLink／部位、範本等階、主屬性資料與 `sx` 類型。未解讀的 tz 其餘欄位維持未知，不猜測用途。摘要綁定 E1–E9 目標子樹、主屬性公式與實際讀取表欄，來源仍綁全部 15 指紋；不能只以 tz 檔案未變判定可沿用。

**建議基準存檔條件（尚未取得套裝首次證明）：**

1. 來源、原始存檔雜湊及隔離副本來源可追溯；既有合法存檔能由同來源遊戲正常讀取。所有測試列只在 repo 外副本準備，玩家原檔唯讀。
2. z7 有數量 1、owner=0 的原生有效套裝；z9 分別有未穿戴與已穿戴套裝。y0 合法但不要求等於目前列號，搬移會保留來源列資料（E8：2874／2875）。
3. 已穿戴者 z9 y7 與 z2 `[角色,15+slot,2]` 必須唯一且雙向一致；z9 未穿戴者不得被角色引用；角色指標只定位 z9，不以同列號誤擋 z7（E9：801／15）。角色存在且可刷新，涵蓋 1、2、3、4 個有效部位、混套與不同 y23 的同套組合（E4–E6）。
4. Q1–Q6、T1–T9、合法詞條／係數及完整 y23／y26／y27；至少保留原生合成前後對照。y23 的生成合法性不能用 y5 代替；y27 對得上實際合成原範本；異常／缺來源 metadata 的列先拒絕（E1、E6、E7）。
5. 能準備足額、恰足與不足的銅錢來驗單次／最大升級；魂魄獨立監看。資源量依該 T／L 公式計算，不固定複製普通裝備情境的常數（E2、E3）。

## 5. V1.0.11.2 合成後的搬移與歸屬

**靜態核對：合成原位改寫所選庫，沒有先把裝備搬入 z7。** E7 的裝備資格讀取與五個 SetXYZ 均使用 `选择库序号`；依序保存 y27、替換 y1、標記 y24=1、寫 y23、y26。此子樹不改 y6、y7 或 z2 穿戴指標。選庫為 9 時再以該列 y7 呼叫 `刷新单角色全属性`（3610）。所以穿戴中合成仍應維持原裝備庫列與歸屬，不能沿用「先取下再合成」假設。**未知：** 選庫與歸屬在實際 UI／存讀中是否都符合這條路徑，未實測。

**靜態核對：搬移另走 E8。** 存入／取出逐欄複製 **y0–49，共 50 欄**到目標空列，來源這 50 欄逐欄清零（2874／2875；迴圈 expression 59=50）；目標列號可能改變。不能把存檔的 60 欄尺寸誤當成搬移範圍，y50–59 未由此子樹處理，須另監看。穿戴／卸下另由 E9 更新雙向指標。首次證明須分開驗「z7 合成後搬入並穿戴」與「z9 穿戴中原位合成」，並比較整列 metadata 與指標；不能用合成子樹沒有搬移動作推論所有後續搬移已安全。

## 6. go 後的群組、oracle 與首次矩陣

以下均是**建議，尚未實作／執行**；遊戲規則依據為 E1–E9。

### 新群組與開放範圍

- z7：`backpackSetEquipmentLevel`；z9：`setEquipmentLevel`，兩個獨立可寫群組、兩份首次證明。只改既有套裝 y6；不開品質、詞條替換、合成、metadata 或超限操作。
- 共同資格檢查需識別套裝範本／setLink、原版等階品質、現有等級、完整 metadata 與有效歸屬。不得直接移除 `ordinaryEquipment` 的排除後沿用普通群組。z7／z9 不互相代證（E1、E7–E9）。
- 新 section／family（`initialProofRequired`）、代表情境、需求表、suite、proof、oracle 與生命週期腳本須一起落地；在 `verification-requirements.cjs`、`verification-suite.cjs`、`migration-scenarios.cjs` 與相應測試宣告。現有 migration 的 `equipment()` 明確只造普通裝備，不能當套裝基準。
- v2.8.1 的排除維持到各自首次證明通過，之後依套裝自己的群組取代排除。不要回復歷史上 z9 以普通證明接受套裝的路徑；核心修改另按技藝上限整檔摘要規則處理（[下一版計畫](next-version-plan.md)第 2 節）。

### 獨立 oracle

1. **寫入 oracle**：預期只有指定 y6 token 改變；其餘文字與大型整數 literal 保留。特別逐欄見證 y23／26／27、y7、y0、品質、詞條及穿戴指標不變。undo／累計還原、非法目標與不合格列拒絕後全檔不變（E2、E7–E9）。
2. **效果 oracle**：獨立實作單件主屬性／詞條、E4 部位最大 y23 與 S、E5 的 N、E6 三類加成及 2／4 件啟用條件；不以被測 core 預覽當答案。呼叫隔離原生 `装备属性计算` 與刷新後角色屬性比對，驗 y6 效果改變而 S／N／套裝額外加成保持。現有 tz 沒有六件效果，該分支只做合成靜態單元測試，不能宣稱自然六件實測。
3. **原生升級 oracle**：z9 從同起點執行單次／最大升級，檢查上限、逐次銅錢扣款及魂魄不變；與編輯器同目標等級比較裝備／效果，資源差異另列。z7 先核對原始背包修改，再經原生 E8 搬入取得實際目標列號，才用 z9 升級 oracle，不按舊列號定位（E1–E3、E8）。
4. **IO／生命週期 oracle**：編輯副本載入、刷新、原版存檔、停止、新 PID 讀回；另驗搬入、穿戴、卸下、搬回與原位合成。移動以來源身分／metadata 識別，記錄允許的列號／owner／標記變動，不要求整份存檔 byte 相同；精確 token 保留只適用編輯器匯出階段（E7–E9）。

## 結論：go（進入實作與首次驗證）
