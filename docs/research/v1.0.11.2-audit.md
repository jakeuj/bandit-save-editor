本機以 `appmanifest_4267800.acf` 的 buildid 及新 `package.nw` 解包後指紋確認來源，沒有只依包內版本文字判斷。

## Windows 隔離驗證

沿用 `verify-migration.cjs`、新版候選 catalog、安裝所附 runtime、隔離 profile 與 Steam 寫入鏡像。保持真實 Steam 初始化及靜音，玩家原始存檔只作唯讀來源。

本輪 Windows 的第一輪在已通過副本的清理階段遇到檔案鎖 `EPERM`，未寫回證明；改用既有 `--keep-copies` 重新執行。後續在技藝上限的 checkpoint 重啟後遇到 HTTP 連線中斷；`verify-game.cjs` 的 CDP 探索請求改用 `Connection: close`，讓同一 Node 程序不再重用上一個 NW.js 的 HTTP socket，修正後代表案例的原生經驗／存讀重啟通過。原始診斷保留在 repo 外。

最終 15 個副本、245 個流水線步驟通過，24 個既有群組全數開放。四個品質副本各完成 6,592 組原生公式比對；技藝上限使用兩角色代表矩陣與兩角色生命週期，保留上一版首次 108 角色完整矩陣證明，沒有把代表遷移改稱首次完整驗證。基礎資質另含 Q1／Q6 的 8 角色代表矩陣及兩角色生命週期。

恢復時保留同一候選來源已通過的 11 個副本，重跑技藝上限代表案例與生命週期，並完成兩個基礎資質副本。對所有完成紀錄重查唯一副本名稱、全部 15 來源、原始存檔及技藝上限 binding／原生觀察後，透過既有 `provenChecks`／`writeBack` 合併新版證明。未完成的嘗試均沒有寫回旗標。Windows checkpoint 的 CLI 另補輸出 flush 後結束，避免已輸出 PASS 卻因除錯 socket 收尾而逾時。

## 最小遊戲 UI 補測

以新版來源建立獨立副本，六件品質案例涵蓋兩庫各 Q1→Q2、Q5→Q6、Q6→Q5；另兩件 Q3 涵蓋未選槽及編輯器先選槽2。原生函式讀檔；洗練入口經世界→萬魂塔→地區紫色圖示到達。後續各目標切換以原生函式準備，實際洗練與停用槽點擊透過 Windows computer-use 執行，沒有把準備動作當成 UI 導覽證明。

八次實際洗練均扣 100 魂魄，僅允許目標槽 ID／係數／旗標變更；提示造成的新取得標記 1→0 另行核對。所有其他目標欄位保留，詞條來自合法池、係數符合品質範圍且只有唯一選槽。兩次停用槽點擊的完整觀察資料不變。可見品質為綠／紅／橙、詞條數為 1／5／4，上限提示為 15／35／30。

先獨立核對上述資料，再建立最終 IO 基準；原版存檔、兩輪 assert、停止及新 PID 讀回通過，測試程序已停止。UI 證明綁定本輪事件 SID 與新摘要，沒有沿用舊摘要。
