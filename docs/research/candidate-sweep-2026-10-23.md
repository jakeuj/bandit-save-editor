## 1. 小數丹藥：限制跨越三個功能

重新核對 `服用普通丹药` SID **660833363431874**，三項寫入 SID **880300005151299／669100206862089／405296456902521**，本版 expressions **2265–2267**：

`Bnew = clamp(clamp(B + 10×E×數量, 0, 10×C−baseRaw), 0, 10×(P−A))`

仍是內層用原始基礎值、外層用完整 A；不可把兩者換成同一式。完整背景見[第二批研究](advanced-editing-batch2.md)。舊文 expressions 2255–2257 是舊版定位，不套用到本版。

**新增的程式關聯核對：**

- `pillInfo` 將 max 向下取整，且 current 必須為安全整數；`setPillAptitudeBonus` 也只收整數。
- `randomCharacterGrowthInfo` 與天賦預覽分支另有 `Number.isSafeInteger(bonus)`；只放寬丹藥 API，仍會留下合法小數角色不能調整基礎資質／天賦的斷裂。
- 三者共用 `aptitude:角色ID` 累計還原群組。小數支援必須涵蓋丹藥→基礎資質→天賦，以及反向操作順序、undo 和整組還原。
- `characterAptitudeSource` 目前拒絕結丹／重生紀錄及尚未涵蓋的穿戴資質來源。小數功能不需要同時擴大這些範圍。

**算術示例，非原生角色見證：**令 baseRaw=11、A=1.1、M=1.5、P 足夠高，C=1.65，原生內層端點為 B=5.5；現行 max 向下取整只給 5。這說明原始 B 的 0.1 對應顯示資質 0.01，而非一律 B 每 1。仍需合法角色與原生服藥取得相同類型端點，不能用此算例代替首次證明。

建議首輪保留「直接指定增量、不扣材料、以已持有丹藥為上限依據」語意。目標數值以明確十進位格線驗證；既有值可能帶二進位浮點尾數，應先以原生存讀樣本決定可接受誤差，不能在載入時四捨五入原始 token。也不能直接採任意 epsilon 放寬上限。若使用顯示四捨五入後比較，須另驗相鄰兩個原始值顯示相同但超出原始端點的情境。

最小驗證表：三項資質 × 0／小數端點／端點前一步／端點後一步，另加既有浮點尾數、下降／歸零、原生下一次單顆／最大服藥、重生清零、具名 API 與自訂座標拒絕繞過。精度方案確定前不宣稱所有小數都支援。

另以 Node 的 IEEE-754 算術代入同一端點式（仍非原生遊戲測試）：baseRaw=69、A=6.9、C=10.35、P=10 得 B=`30.999999999999996`；baseRaw=71、P=10 得 `29.000000000000004`。連理論上整數的端點都會有尾數，故單純把檢查改成 `Number.isSafeInteger(B*10)` 仍會誤拒。輸入目標格線與既有原生數值資格必須分開設計；實際遊戲序列化結果待獨立見證。

### 實作摘要（2026-10-24，v2.13）

依[輕量開發流程](../maintenance/lightweight.md)直接實作，限無結丹，不建 SDD。對話決定的兩項政策：

- **輸入格線 0.1**：B 最多一位小數（資質 0.01 步進，對應遊戲顯示兩位小數）。上限 `max=floor(100×(min(C,P)−A)+1e-6)/10`，仍是 v2.2 的保守產品限制（外層完整 A），不是原版雙 clamp 的逐字等價。浮點尾數端點（例如 30.999999999999996）落回格線 31，不會少一格。
- **原始浮點保留**：載入不四捨五入；既有 B 只要是非負有限數值就可讀，資格仍以原始值算總資質不超上限。`pillInfo` 回傳原始 `current` 與格線 `display`；填回同一顯示值回傳 `unchanged`、不寫入，原始 token 逐字保留。

**欄位與入口**：只寫 `[角色,13–15,2]`，入口仍為 `pillInfo`／`setPillAptitudeBonus`（`aptitude:角色ID` 還原群組不變）。新旗標 `pillAptitudeBonusDecimal`（冒煙通過後已開）；關閉時行為與 v2.2 完全相同（整數、小數 B 唯讀）。開啟後一併放寬 `randomCharacterGrowthInfo` 與天賦預覽的 B 讀取檢查（`assertPillBonusReadable`），基礎資質與天賦會照常因小數 B 超上限而阻擋。旗標登記在 batch2 family（`verification-requirements.cjs`／`verification-suite.cjs`），重建 batch2 規則時與既有丹藥旗標一起關閉。

**拒絕條件**：非數值、NaN／Infinity、負數、超過一位小數、超過 max、`advanced`，以及丹藥主旗標未開。自訂座標與 `setField` 仍唯讀。

**合成測試**：`tests/pill-decimal.test.cjs`，涵蓋旗標關閉、三項資質 0／15.4／15.5 端點／15.6、浮點尾數端點、既有尾數 token 保留與 undo／restore、基礎資質群組相依、天賦預覽讀小數 B、自訂座標不可繞過。

**隔離遊戲冒煙（2026-10-24，V1.0.11.2 完整快取，通過）**：`verify-game.cjs` 以目前 core 編輯基準存檔。角色 1（範本 0、無結丹，A=4.3／3.2／3.0）寫入 21.5（力量端點，總資質＝C 6.45）、7.3、12.4；角色 8 是基準存檔裡原生留下 B=17.5 的角色，力量填回 17.5 走未修改路徑（token 原樣），敏捷 16→15.5。雲存檔載入、原版存檔（原生寫出 `21.5`／`7.3`／`12.4`／`17.5`／`15.5`）、停止後以新 PID 從存檔讀回皆一致。`verify-native-lifecycle.cjs` 原生各服一顆藥：力量在端點不消耗也不增加，敏捷 7.3→16、智力 12.4→15（皆等於編輯器上限），`角色重生` 清零；之後再原生存檔核對通過。基準存檔雜湊不變，結果留在 repo 外的 `pill-decimal-20261024/result.json`。

## 2. 結丹丹藥與內丹：先做唯讀依賴

`角色资质上限倍率` SID **358500068340403**，expressions **4058–4060** 仍由角色 y50 的整數次數，逐次讀 `z16[角色,2k]` 引用的 `z17[內丹,15]`，最後加 1.5。

`内丹属性计算` SID **709738476735942**，expressions **5380–5381** 另經同一引用讀內丹範本、等級、等階、主係數及品質，再呼叫裝備主屬性公式。因此 **A 與 M 同時受內丹影響**，不能只擴大 cap 倍率。

`渡劫结束` SID **248151541683973** 的成功分支 **963468871617308** 會搬移入體、清除角色裝備欄、改角色等級及 y50、寫 z16 品質／內丹引用與 z17 owner；子事件 **448872290783748** 寫 z17 y9–11 為 107–109、y15–17 為結丹資質提升係數。`内丹入体存入` SID **602328981829577**／子事件 **905333709115389** 搬移 z9→z17 的 y0–49。這是跨層交易，不是獨立 y6 修改。

**新查證：** `获得内丹经验` SID **993397580653400** 的事件本體無 actions／children；`内丹升级经验` SID **717223484505453** 有 expression **3649** 的需求公式，但本輪掃描事件樹中的直接函式 action 與 expression 綁定引用，兩函式呼叫數均為 0。這不涵蓋任意動態名稱呼叫，因此只能說本輪未找到可用經驗流程；不可因存在需求公式而新增經驗編輯器。

下一切片先輸出唯讀 A、M、C 與每筆引用來源，拒絕缺列、錯類型、owner 不符、重複／越界引用，再與原生函式對照。結丹丹藥可先只改 B；內丹品質、渡劫成功狀態及階段跳轉各自另案。後續驗證需要成功／失敗分支、存讀／重啟及再次結丹；本輪沒有執行。

## 3. 靈物：共同生成與衍生平均值

`获得灵物` SID **699971245656002**，初始化子事件 **576913073008767**：z18 y1=範本、y2=等級、y3=範本類別、y4=品質、y5–9=五行、y10=平均值、y13=新取得標記。五行來源的 `lw` 表有 33 個非標頭列，本輪逐列檢查五項基底皆為正數。

expression **2856** 再算 `y10 = round(10×Σa_i/5)/10`。因此各欄單獨落在看似合理區間，不足以證明五欄能共同生成；y10 也不能獨立指定。逐項取整後的 Σa_i 不必精確等於 G，不應用「總和完全等於 G」誤拒合法資料。

**呼叫閉包（V1.0.11.2 靜態，含動態座標）**：
- 城市 y11 的寫入者：一般遊玩只有 `挑战胜利`（+1 後呼叫 `获得声望`）。`加层`／`减层` 改 y11 的分支與「初始化全部設 148」都只在開發模式。
- `[8,1,0]` 只由 `获得声望` 寫。讀檔時**不會重算**（只有開發模式會）；`山寨扩张` 門檻、頂部聲望條與擴張頁面都讀快取。所以只改 y11 會讓總聲望停在舊值，直到下一次挑戰勝利。
- 動態 y 寫入：`城市派驻`／`城市召回` 寫 y40–42，`升级城市` 寫 y22–25，碰不到 y11／y44。
- y11 的讀者只做門檻或顯示：
  - 城主府聲望獎勵（`解锁图纸`／`解锁装饰建筑`，要玩家領取，門檻是層數序號×10）。
  - 酒館招募（js 第 59 欄）、兌換（wp 第 19 欄）、引導任務（`[1,11,0]`）。
  - 挑戰難度＝y11+1+zddt 第 6 欄；`开始城市波次` 要 y11+1＜`城市层数上限`（150）；y11≥149 出現攻城。
  - 降低層數不會收回已領的獎勵或已完成的任務。
- `生成战斗地图` 發現 y21 不在 0–y11 時把它夾回 y11；`挑战胜利` 只在 y21=y11 時讓 y21 跟著 +1。

**使用者決定（2026-10-24）**：
- 0–149 可升可降。
- 沒進過的城市（y44≠1）拒絕。
- 升高不動掛機層數；降低時 y21 超過新值才夾到新值。
- 已佔領（y38=1）的城市不能低於 149。

**欄位與入口**：
- 寫 `[c,11,0]`；總聲望 `[8,1,0]` 在同一筆交易依原式重算；降低且 y21＞新值時寫 `[c,21,0]`。
- 獨立入口 `cityLayersInfo`／`previewCityLayer`／`setCityLayer`。還原群組統一為 `city:layers`，因為總聲望是各城共用的快取。
- `resolveField` 新增一個分支，把城市列的 y11／y21／y38／y44 標為已知唯讀。原本這幾格是未辨識欄位，自訂座標可以直接寫。
- 城市名稱放在 catalog 的 `cityLayers`（`scripts/city-layer-data.cjs` 產生，另記 `zddt.json` 的 SHA-256）。
- 不併入 15 個來源指紋：`migration-proof` 固定核對 15 項，併入會讓既有群組的證明檢查全部失敗。靜態快取沒有 `zddt.json` 時，擷取沿用同版本的舊區塊；區塊內容改變時關閉旗標。
- 新旗標 `cityLayerLevel` 登記在 batch2 family；UI 在「山寨與科技」（`src/city-ui.js`）。

**拒絕條件**：
- x 不是城市列、城市沒進過，或已佔領城市要降到 149 以下。
- 任一城市的 y11 不是非負安全整數、y44 不是 0／1；目標城市的 y21 不是非負安全整數、y38 不是 0／1；`[8,1,0]` 不是有限數值。
- 新值不是 0–149 的整數（字串、小數、NaN、150 都拒絕）。
- 新值與目前相同時視為 `unchanged`，不寫入。
- 存檔原本的快取和公式不符時不拒絕：預覽標示出來，套用時寫回正確值。
