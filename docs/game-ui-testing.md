# 遊戲驗證範圍與 UI 測試操作手冊

## 適用範圍與證據

本手冊補足 computer use 的操作與驗收脈絡；精確公式、SID 與來源指紋仍以研究文件為準。現有 v2.3 的 380 組效果、76 次洗練證據來自隔離遊戲原生函式及存檔 IO，並非 380 次滑鼠操作。完整遊戲選單導覽不是預設交付項目；未操作的 UI 不列為已驗收。

2026-10-23 使用者核准改為按影響驗證：高頻改版不操作遊戲桌面，UI 顯示／互動疑慮先記錄，實際出問題再複查。既有功能的遷移不再受 UI 摘要異動阻擋；使用者明確要求 computer use 才進入「快速開始」。新增寫入的首次證明仍保留；編輯器網頁與 PWA 以獨立 headless 驗證。新的日常入口見[版本遷移重驗](maintenance/migration.md#版本遷移重驗)。

| 證據 | 可證明 | 不能代替 |
| --- | --- | --- |
| 合成／核心測試 | 邊界、交易、原文保留 | 遊戲載入及 UI |
| 隔離原生函式與 IO | 公式、存檔／重啟、原生後續動作 | 選單路徑、按鈕資格與面板即時顯示 |
| 遊戲 UI 操作＋截圖 | 可見狀態、選槽限制、實際操作結果 | 未測範圍與其他版本 |
| 網頁 UI／PWA | 編輯器流程、匯出讀回、離線 | 原生遊戲 UI、直接 file:// |

## 快速開始

接到「用 computer use 實際測試遊戲」時，先依此順序到達可操作畫面，再走下方已驗證路徑。這份手冊維護遊戲知識；工具初始化、API名稱與權限以當次可用的computer-use技能及工具文件為準，避免重用過期連線方式。

1. **選定要證明的UI行為。** 例如「首次選槽後另一槽停用」，取一件未選槽、一件編輯器已選槽的普通裝備；完整數值矩陣沿用對應研究。完成標記：每件有庫別、目前列號、範本、品質、詞條與旗標的初始快照。
2. **準備隔離副本。** 核對來源後沿用`verify-game.cjs --help`的setup／state流程；隔離profile、存檔與證據放repo外，保留原生Steam初始化及靜音。載入方式先標明原生函式或實際UI，兩者分開記錄。
3. **打開正確視窗。** 工具預設`package.json`的`window.show=false`；只將測試副本設為可見，再以隔離程序路徑／PID核對視窗清單的標題與ID。舊state內的PID或舊視窗ID不能直接當目前目標。完成標記：取得該副本當下截圖，能辨認主畫面與測試資料。
4. **恢復畫面更新。** `--probe`及`--assert`會在「主界面」呼叫`SetTimeScale(0)`；已完成原生載入但畫面黑色時，檢查是否停在淡入動畫。若本次工具允許隔離runtime測試準備，恢復該副本時間為1，等主畫面顯示再操作；此動作不算UI讀檔。後續再次probe／assert後，繼續UI前也要檢查暫停狀態。
5. **依完成標記前進。** canvas無可用節點時，從最新截圖找圖示或文字，執行一步後取得新畫面；畫面尚未切換時重新觀察，別重按同一位置。到達目標頁即可開始代表案例，不再探索其他系統。
6. **完成生命週期。** 每個有效動作記錄可見結果、成本及允許變更欄位，再做原版存檔／停止／新PID讀回與原始雜湊核對。完成後停止自己的隔離程序，留下可接續的state與證據索引。

目前可見遊戲參考為 Windows、V1.0.11.2／build 26126719、2560×1440，洗練選槽與品質最小補測見[V1.0.11.2 紀錄](research/v1.0.11.2-audit.md#最小遊戲-ui-補測)。早期 V1.0.10.2 畫面屬歷史參考。這是辨識畫面的參考，不是固定點擊座標；縮放、DPI、布局或版本不同時先核對新畫面。

## 預設驗證流程

先依版本遷移選跑，語意未變可沿用原始實測，不必啟動遊戲。需要補原生證據時：

1. 核對安裝來源與該群組完整指紋，在 repo 外建立固定存檔及隔離副本；保留原生 Steam 初始化與寫入鏡像。
2. 由核心 API 產出候選修改，啟動真正遊戲並載入；比對原生公式及相關後續行為，例如洗練、卸穿或服藥。這是遊戲內函式執行，不是只在編輯器重算公式。
3. 透過原版存檔流程寫檔，停止隔離程序，以新 PID 重啟並讀回；核對修改值、關聯、效果及原始存檔雜湊。未變的後續生命週期可沿用，實際跑過的階段才記為本版原生通過。
4. 明確報告「隔離遊戲原生函式／IO／重啟讀回通過」及未涵蓋範圍。未操作選單，不寫成「遊戲 UI 已通過」。測試結束只關閉自己的隔離程序，保留 repo 外證據。

不用為每次修改額外補齊滑鼠選單路徑或截圖，也不將缺少全套遊戲 UI 導覽視為原生驗證的未完成條件。編輯器網頁的選檔、預覽、還原、匯出、讀回及PWA驗收優先由Node與獨立headless執行，見[程式化測試指引](testing.md)。本文件的computer use步驟僅在原生視窗、使用者特定環境或程式無法回答的具體問題需要補證時使用。

## 測試音量

隔離驗證預設靜音。`scripts/verify-game.cjs` 的共用啟動流程固定加入 `--mute-audio`，涵蓋新建副本及既有 state 的每次重啟，從啟動音樂開始抑制輸出。此為 [Chromium 自動測試的音訊靜音參數](https://chromium.googlesource.com/chromium/src/+/06e87fb3dc2a1c881f95eb6cd3738608b846d29a/media/base/media_switches.cc)，不改遊戲存檔音量、正式安裝、Windows 主音量、其他遊戲或 Discord 設定。

不要為了測試自動恢復聲音；只有使用者明確要求音訊驗收時才另安排有聲測試。手動啟動隔離副本也須帶相同參數，避免繞過共用啟動器。此參數不會追溯套用至已啟動程序；需在確認測試存檔後停止自己的副本，再以靜音參數重啟。本次只檢查啟動設定與程式，未為驗音重新播放遊戲。

## 何時才補做遊戲 UI 測試

- 遊戲可見數值、提示或即時面板與原生公式／持久資料不一致，例如懷疑舊效果快取殘留。
- 要驗證選單、按鈕啟用條件、初次選槽或確認流程；這些條件可能在原生函式呼叫端之外。
- 修改或診斷遊戲輸入、視窗、解析度、啟動顯示，或問題只在實際操作時發生。
- 使用者明確要求實際遊戲畫面、操作導覽或截圖證據。

上述情況先做原生／存檔診斷；需要桌面證據時說明缺口，使用者明確要求後只驗最小代表流程。UI 結果不取代來源核對、原版存檔與新程序重啟。

開始前說明具體未確認問題，以及原生函式／存檔證據為何不足；取得目標完成標記即結束。工具受阻就記錄缺口，繼續獨立的原生診斷；既有功能的改版不為缺少 UI 截圖而關閉。

## 版本遷移後的 UI 補測

新版遷移以複合證據將 `selectionUi`／`qualityUi` 記為 `source: "deferred"`，意思是本版 UI 未重驗；保留摘要供日後定位，不把它填成原生通過，也不阻擋既有功能。舊版 `pending` 後補 UI 的流程是歷史規則，例行改版不再執行。

實際故障且使用者要求桌面操作時，可從以下最小案例選擇：

- `selectionUi`：一件未選槽、一件編輯器已選槽的普通裝備，確認首次洗練後其他槽停用，且已選槽只允許同槽。路徑見下方「V1.0.11.2 洗練入口與隔離視窗」。
- `qualityUi`：兩庫各做一次升品與降品，確認提示顏色、等級上限、詞條槽數與可洗練槽一致，取法同[品質研究](research/equipment-quality.md#代表遊戲ui與網頁驗收)的六件案例。

取得完成標記後接回原版存檔與新 PID 讀回，另記實際 UI 版本與結果；不要為了改寫既有的 `deferred` 狀態重走全部案例。新增功能的首次 UI 證明仍依該功能原始規格處理。

## 開始遊戲 UI 測試前

1. 先讀 `docs/maintenance.md` 和對應研究，核對安裝 build、完整 13+2 來源及 repo 外隔離 state。保留原生 Steam 初始化與測試鏡像；不把正式玩家存檔當測試工作檔。
2. 先確認當次工具是否提供原生 Windows 視窗控制。有則按該工具及 computer-use 技能的實際文件操作；若只有瀏覽器能力，記錄「原生遊戲 UI 尚未驗收」，不要把透過除錯介面呼叫遊戲函式改名為 computer use UI 實測。
3. 從視窗清單以隔離程序 PID、標題與路徑辨識目標，不把正式 Steam 遊戲視窗混入。記錄遊戲版本、解析度、視窗尺寸、DPI、語言、存檔槽及初始畫面。
4. 優先沿用已相符的隔離工具建立測試資料，UI 只跑與使用者操作有關的代表案例；完整公式矩陣仍交由可重複工具核對，避免每個候選都重走選單。

## 按需建立的遊戲畫面導覽

僅在需要 UI 驗證時選用下列相關項目，不要求全表每次重跑。第一次實際操作時，記錄每一步的「畫面名稱／可見文字或圖示、動作、完成標記、截圖檔名」。優先可存取性節點；canvas 無節點時，以當次截圖定位，不沿用舊截圖絕對座標。目前不填入猜測的快捷鍵或按鈕位置。

| 流程 | 必須取得的 UI 證據 |
| --- | --- |
| 啟動→讀檔→遊戲主畫面 | 正確測試槽、角色／山寨辨識、可操作狀態；非僅到標題畫面 |
| 普通裝備→詳細資料 | 範本、品質、等級、詞條名稱與可見效果；對照單件預覽 |
| 選槽→同槽再次洗練 | 初始選槽資格、唯一槽限制、成本顯示與實扣；重啟後限制仍在 |
| 穿戴→卸下→穿回 | 使用正確裝備格，面板效果移除／加入，無殘留舊效果 |
| 遊戲存檔→退出→新程序讀檔 | 原版 UI 存檔完成、新 PID、同槽新值與效果，原始存檔雜湊未變 |
| 丹藥（任務涉及時） | 道具資格、上限、服用後顯示；與持久增量及小數限制分開記錄 |

原生卸穿有延後動作：驗證工具曾需要等待約 500ms；UI 測試應等畫面完成標記而不是把固定延遲當成功。裝備搬移可能改目前列號而保留 y0 初始背包列號，追蹤範本、詞條與雙向指標，不假設序號保持原值。

最小代表案例使用兩件外觀相同、初始狀態不同的裝備即可。v2.4使用等階1／品質3的勇武頭巾（範本16）；以庫別＋目前列號及詞條快照區分，別只憑圖示認物。隨機洗練不保證產生新ID；依當次結果比對合法池、係數、效果與成本，不把歷史隨機數值當固定預期。

背包物品的小鎖操作會改物品鎖定欄`y22`，與洗練選槽無關。若不慎點到，立即記錄前後差異，將此UI副作用與被測操作分開；不要把它歸因於編輯器，也不要為了通過斷言放寬整件裝備的允許變更範圍。

v2.5最小品質UI案例為兩庫各Q1→Q2、Q5→Q6、Q6→Q5：核對綠／紅／橙品質、15／35／30上限、1／5／4槽及正確效果。未選槽Q2可首次洗練；原選槽2升降後仍只有槽2可按，新增尾槽保持不可洗練。六次實際按鈕操作各扣100魂魄，停用槽點擊不變。詳細原生矩陣及新PID讀回見[品質研究](research/equipment-quality.md)。開啟提示可能由遊戲清除y24新取得標記，獨立核對僅1→0，再建立後續IO預期。

### UI動作後接回原生存檔驗證

`verify-game.cjs`的`state.expected`來自初始候選，隨機洗練後不再是最終預期。先保存UI前後快照，獨立核對魂魄差額、目標槽ID／係數／旗標、其他槽與其他裝備不變；全部符合時，才將已驗證結果作為後續存檔／重啟比較基準。不能直接把目前值抄成expected就宣稱UI正確。

以下是原生IO階段的命令順序，`$uiState`須指向當次已核對的repo外state；各步成功才繼續：

```powershell
node scripts/verify-game.cjs --state $uiState --save
node scripts/verify-game.cjs --state $uiState --assert
node scripts/verify-game.cjs --state $uiState --stop
node scripts/verify-game.cjs --state $uiState --restart
node scripts/verify-game.cjs --state $uiState --load --mode 存档
node scripts/verify-game.cjs --state $uiState --assert
node scripts/verify-game.cjs --state $uiState --stop
```

重啟後明確指定`存档`，避免預設`云存档`讀回較早的鏡像。assert涵蓋state.cells、原版寫檔、原始存檔／來源雜湊及Steam初始化；把要核對的關聯欄位納入觀察範圍。這段命令不證明UI點擊存檔／讀檔，若任務要求該部分，需另取得真實操作路徑。

### 工具卡住時的短路徑

| 現象 | 下一步與停止條件 |
| --- | --- |
| 找不到隔離視窗 | 核對程序是否仍在、隔離manifest是否可見，再刷新視窗清單；不啟動正式玩家存檔代替 |
| 截圖仍是前一頁 | 先取得下一張新畫面，確認動畫／載入是否完成，再決定是否重試；避免連點造成額外洗練或成本 |
| 黑畫面但已在主布局 | 依快速開始檢查時間暫停與淡入；不靠盲點推進 |
| 工具初始化或視窗所屬程式驗證失敗 | 更新清單、重新綁定一次；仍失敗就保存錯誤與目標資訊、保留待驗項目。過去的工具失敗不是永久不可用結論，下次任務可重試 |
| 只有瀏覽器控制能力 | 可繼續網頁驗收及原生資料研究，遊戲UI保持待驗；依工具當次支援取得原生控制，不用未允許方式繞過 |

畫面工具曾對AdGuard回報目標所屬程式錯誤，重新綁定也無效；這是該次特定視窗的失敗，不能推論遊戲視窗也無法操作。瀏覽器確認框的恢復方式見下一節。

## 編輯器確認框與選檔

2026-10-21 使用者截圖顯示 `127.0.0.1:8942` 的「目前有尚未匯出的變更…」確認框。這是編輯器 `load()` 的 JavaScript confirm，不是遊戲或 Codex 權限詢問。舊程式只檢查 `model.changes.size`，即使已匯出仍提示；修正後與離頁判斷一致，只在有修改且 `revision !== exportedRevision` 時提示。

- 已匯出修改仍留在變更清單，供預覽及還原；不因下載而清空。再次修改後重新視為未匯出。下載原檔備份不等於匯出修改。
- 測試重新選檔前先確認下載事件及檔案內容；等檔案名稱與目前值更新，再操作分頁。檔案選擇完成並不代表非同步解析已完成。
- 對自己的可丟棄合成資料，可依當次工具的 dialog API 處理預期確認框；對使用者未保存資料先取消，保留內容。不要預設接受所有 dialog。
- 遇到 filechooser／DOM.setFileInputFiles 逾時，先看確認框與目前檔名。模態框可能阻塞後續命令，不能一律判為工具故障；沒有狀態變化就停止重複點擊。處理確認框後再驗證載入；必要時重設工具連線，勿重啟整個使用者瀏覽器。
- 背景分頁仍可能產生前景的原生確認框。只建立必要測試頁，先匯出或還原合成修改，最後清理自己建立的頁面；不要以移除真正的未匯出保護來減少干擾。
