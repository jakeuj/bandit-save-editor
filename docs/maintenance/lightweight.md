# 輕量開發流程

[維護索引](../maintenance.md) · [下一步與目前進度](../research/next-version-plan.md)

2026-10-24 起，使用者決定改用本頁流程：這是使用者自己玩遊戲用的輔助工具，修改器只另存副本、不覆蓋原檔，改壞了換回備份即可。本頁取代舊流程中下列較重的要求：SDD（proposal／tasks，含 A／B 拆分）與另開的設計文件、分派表與多 session 協調、全量原生矩陣、證明紀錄綁定各種雜湊、改 core 就重證全部代表副本、遊戲 UI 證據。舊規則留在各維護文件作為歷史紀錄，與本頁衝突時以本頁為準。

## 保留的保護

- 匯出只替換指定值的 token，保留原文（BOM、大型整數、指數寫法、空白）。
- 核心交易的合成測試：資格、預覽、交易、失敗回滾、undo／還原。邊寫邊補即可，不強制先寫測試。
- 每個新寫入功能有自己的 `verification` 旗標，預設關閉，下方「隔離遊戲冒煙」通過才開。自訂座標、舊 `set` 與批次不能繞過旗標。
- 真實存檔、遊戲 payload、runtime 與原始 log 留在 repo 外，只操作隔離副本；玩家原檔與快取的雜湊不能變。

## 新功能怎麼做

1. **不寫 SDD**：不建 `sdd/<功能>/`，開工前也不另寫設計文件。要改哪些欄位、公式、拒絕條件直接列在當次對話的任務清單；需要使用者決定的取捨（例如輸入精度、範圍限制）在對話裡問。
2. **實作**：新功能仍走[獨立具名入口](core.md#新功能的-core-開發規範)，避免牽動既有功能；這是為了好維護，不是為了少跑重證。
3. **測試**：相關 Node 測試，加一次 `npm run test:browser`。瀏覽器測試涵蓋桌面與 390px 的套用、下載與重新讀取。本機內容過濾器（例如 AdGuard）若改寫 loopback 埠的 HTML，PWA 雜湊會對不上；官方入口開跑前會先檢查並停下提示，照提示設 `BANDIT_BROWSER_PORT` 或加過濾器例外，見[測試指引](../testing.md)。
4. **隔離遊戲冒煙**：每個庫別／方向挑 1–2 個代表案例，用修改器編輯後，在隔離副本以原版存檔，再換新程序讀回，確認數值與原版行為一致。不跑全量矩陣，不做全分母 oracle 對拍。
5. **寫實作摘要**：做完後在該功能的研究文件加一小節「實作摘要」（沒有研究文件就寫在 [`docs/releases.md`](../releases.md) 該版紀錄），只記以後維護會用到的事：改了哪些欄位、公式、拒絕條件、具名入口，以及冒煙用了哪些代表案例與結果。這是事後紀錄，不是開工前的規格。
6. **開旗標、發布**：依[功能收尾最短流程](release.md#功能收尾預設最短流程)。不另寫長篇驗收報告；推送後在回覆最後附下一步提示與可貼上的開工 prompt（同一節第 5 步）。

既有 `sdd/` 目錄保留為已交付功能的歷史規格與證據，維護舊功能時照樣可讀，不需要補寫或遷移。

遊戲 UI 證據預設不做，見[遊戲 UI 手冊](../game-ui-testing.md#新功能首次證明)。

## 改 core 與遊戲改版

- 改 core 不再重證全部代表副本。改到既有功能的程式時，跑該功能的 Node 測試；改動牽涉存檔讀寫行為時，再補該功能的隔離遊戲冒煙。
- 遊戲改版時，對受影響的功能跑冒煙。
- `node scripts/core-slice-report.cjs` 只當參考，不再決定要不要重證。重證成本紀錄（`reproof-ledger.json`）與「並行副本」候選隨之停用。

## Session 與授權

- 預設在同一個 session 做完，不開子 session。查詢或核對用子 agent；只有同時符合「長、機械化、規格已定」，或兩個互不相干的功能要並行時，才依[任務分派](dispatch.md#先判斷要不要分派)開子 session。
- 啟動隔離遊戲、computer use、發布、Wiki／Project／公告同步，仍需使用者當次同意。
- 每完成一個功能，主動把可重用的教訓（工具陷阱、踩過的坑）寫回技能或對應的維護文件。

## 建置閘門

`scripts/build-editor.cjs` 對每個開啟的旗標（`knowledge/catalog.json` 的 `verification`）只核對三件事，任何一項不符就拒絕建置：

1. `knowledge/verification.json` 的 `groups` 有該群組，且為 `true`。
2. `verification.json` 的 `gameVersion` 等於知識的 `gameVersion`。
3. `verification.json` 的 `fingerprints` 等於知識的遊戲資料指紋。

不再核對 core 摘要、證明內容、manifest 或工具雜湊，所以改 `src/core.js` 不會讓建置失敗。新功能冒煙通過後，在 `groups` 加上該群組、在 `verification.json` 的 `lightweight` 加一筆冒煙紀錄（日期、遊戲版本、代表案例、基準存檔與 repo 外結果檔的 SHA-256），並打開旗標。

`lightweight` 裡的群組不進舊的複合遷移證明（`scripts/migration-proof.cjs` 的 `composite`）：選跑、`problem` 與 `compose` 都略過它們，所以版本遷移寫回後這些旗標會關閉，要在新版重跑冒煙再開。沒有這筆紀錄的已開群組仍照舊要求複合證據。冒煙可沿用 `verify-game.cjs --scenario`（`setPillAptitudeBonus`、`setEquipmentLevel` 等具名操作）加 `verify-native-lifecycle.cjs`（`ascend`、`followup`、`pills`、`backpackOverLimit`、`relics`、`relicTakeOff`、`relicStandPrepare`、`placedRelicAura`、`wall`、`city`、`ascensionQuality`、`innerPillPrepare`、`innerPillLevel`、`ascendedInnerPillLevel`、`relicCrafting` 等動作，以 `main()` 的清單為準；`pills` 可用 `pillCharacter` 指定角色；擺放類動作要在存檔重啟後另跑一次取下，才算驗過兩輪 IO；`穿戴装备` 後要等一拍再讀角色指標，同一次 evaluate 內讀到的是空列）；固定基準存檔先複製到 repo 外的新資料夾，步驟依 `.local/game-sources.json` 的 `nativeSmoke` 紀錄（雲存檔載入 → 存檔 → assert → stop → restart → 存檔載入 → assert）。遊戲改版時，對受影響的功能跑冒煙，再更新 `gameVersion` 與 `fingerprints`。測試見 `tests/build-gate.test.cjs`。

`scripts/*-proof.cjs` 與 `verification.json` 裡較早的首次證明紀錄仍保留作為歷史證據與遷移工具，但不再是建置條件。

### 測試也不綁目前 core

2026-10-24 第一次在輕量流程下改 core（小數丹藥）時，有 21 項舊測試失敗：它們斷言「已開放群組的首次證明、B7 等價或 core 切片基準必須對上目前的 `src/core.js`」。依使用者決定已刪除這些斷言（`tests/helpers/set-quality-shipped.cjs` 的 `assertShipped` 只核對旗標與群組紀錄存在）；切片選取機制測試改以目前 core 當基準。之後新增測試不要再把歷史證明綁到目前 core 文字或切片。

新增旗標時，除了 `extract-game.cjs` 的預設值與 `catalog.json`，也要登記到 `scripts/verification-requirements.cjs` 與 `scripts/verification-suite.cjs` 對應 family 的 `groups`，否則 `version-migration` 測試會報「no family」；旗標開啟前，`version-migration.test.cjs` 的 write-back 比對清單也要列入它（開啟後自動排除）；但 family 設有 `initialProofRequired`（例如 randomCharacterTalents）時，write-back 不會開它，不要列入（v2.17 教訓）。core 以 `vm` 載入，回傳的陣列屬另一個 realm，`assert.deepEqual` 會報「same structure but are not reference-equal」；先展開（`[...x]`）或只比長度再比較。

`verify-game.cjs` 的操作白名單新增具名方法時，也要把它（與對應的 info／preview 入口）列進 `scripts/migration-analysis.cjs` 該 family 的 `coreRoots`，否則 `tests/core-slice-roots.test.cjs` 報「不屬於任何 family」。新的 UI 模組（例如 v2.15 的 `src/relic-ui.js`）要在 `build-editor.cjs` 加佔位替換、在 `tests/skill-caps-ui.test.cjs`／`tests/talent-levels-ui.test.cjs` 兩個完整 UI 測試台注入，並在 `knowledge-ui.js` 呼叫處加 `typeof` 防護（單獨載入 knowledge-ui 的測試沒有該函式）。重抽 `catalog.json` 時鍵順序可能和既有檔不同，以語意比對確認沒有其他差異即可。

改到 `editingInfo`、`setEditingValue` 這類共用樞紐（v2.14 背包超限）時，所有 family 的切片都會變，`migration-proof` 的 `problem()` 對歷史證明一律回「複合證明與來源或程式不相符」。比照上段：直接斷言「開放群組的證明對上目前 core」的測試改成只核對群組紀錄；要測證明結構檢查（缺首次紀錄、交換、資料雜湊）的測試，用 `tests/helpers/current-core-proof.cjs` 把複本的 core 身分換成目前來源再測。換身分後原生證據摘要仍綁舊切片，所以不能再斷言整體 `problem()` 為 null。

### 基準存檔缺狀態時先原生備料（v2.16 教訓）

固定基準存檔沒有要測的狀態（例如結丹角色）時，不要手寫存檔欄位。先用一次隔離副本做原生備料：雲存檔載入，接著用 `verify-native-lifecycle.cjs` 呼叫原生函式做出狀態（`ascend` 是範例：`获得物品`→`穿戴装备`→設定變數後呼叫 `渡劫结束`），然後原生存檔、新 PID 讀回。最後把該副本的 `save/ea1save.dat`（連同 `saveinfo.dat`）複製到 repo 外，作為新的 `--save-file` 基準，再照常跑編輯冒煙。踩過的坑：

- 事件表的 static local（例如 `渡劫结丹品质`）不在 `GetAllGlobalVariables()`，要從 `GetAllLocalVariables()` 依名稱找，名稱須唯一。
- `verify-game.cjs` 的 `editSave` 每次都會改角色 1（等級、y50 歸零、名稱與經驗），所以要測的狀態放在別的角色。
- `--setup` 在讀 `--scenario` 前就建好副本目錄；情境檔路徑錯時，要清掉殘留目錄再重跑。Git Bash 的 `node -e` 寫檔要用 `H:/...`，不能用 `/h/...`。
- 半途失敗時，遊戲內狀態已經變了，不要在同一副本續跑，從 `--setup` 重來。
- 原生行為和預期不同時（例如重生只清第一筆入體內丹），先在現場讀值確認，再決定是修正拒絕條件還是工具斷言，並把它寫進實作摘要。

### 先用呼叫閉包核對「某原生流程不碰哪些欄位」（v2.18 教訓）

要把既有功能放寬到新狀態（例如結丹角色）時，先確認造成該狀態的原生流程不寫功能依賴的欄位，就能沿用原本的見證與交易，不必重做規則。做法：用 `scripts/extract-game.cjs` 的 `inspectGame` 讀本機來源，從 `g.project[6]` 找出函式事件（`v[0]===4` 且 `v[4]` 等於 `g.functions` 的 sid），沿 `-2`／`5` 的函式呼叫 action 求出呼叫閉包；再把閉包內函式在固定座標索引（例如 `candidate-sweep-20261023/index.json` 的 `operations`／`reads`）的寫入依 z、y 過濾。閉包會多算 UI 刷新函式，沒關係；要另外看動態 y 的寫入落在哪些 z，並在實作摘要寫明固定座標索引的限制。腳本放 repo 外。

### 會隨遊戲時間變化的欄位與修改器算不準的原生值（v2.19 教訓）

- 修改一個值、連帶影響另一個狀態時（例如降級後目前生命會不會超過上限），除了查寫入者，也要查**有沒有原生流程會把它拉回範圍**。城牆的回血與治療都只在「低於上限」時觸發，沒有流程會往下壓，所以降級必須自己處理生命。
- 修改器算不準的原生值（例如含科技與司職加成的 `城墙最大生命`），冒煙時直接在現場用 `verify-native-lifecycle.cjs` 的 `call('函式名')` 取回傳值，和修改器的下界或預期值比對；不要在工具裡重寫一份加成公式。
- `verify-game.cjs` 要等版面進入 `主界面` 才凍結時間（SetTimeScale 0），載入到凍結之間可能已經跑過一次每秒事件。目前生命低於上限時，新 PID 讀回的引擎值會多一次回血，`--assert` 的引擎比對就不會過。這時改看遊戲寫出的存檔與修改器重讀；若要讓 `--assert` 能通過，就讓該欄位在存檔時已在穩定點（例如生命已滿），或者不把它放進 observe。

### 衍生快取、動態座標與 15 項以外的資料表（v2.20 教訓）

- **衍生快取**：改了來源值（例如城市層數），要查衍生快取（例如總聲望 `[8,1,0]`）**讀檔時會不會重算**。總聲望只在 `获得声望` 重算，讀檔不會；擴張門檻又只讀快取，所以修改器必須在同一筆交易依原式重寫快取。冒煙時用 `call('重算函式',…)` 比對修改器寫入值，不要只比自己的公式。
- **動態座標**：`inspectGame` 的 `reads` 會記下 x 為 `*` 的讀取，但寫入的 y 是動態運算式（例如 `39+任命序號`、`21+刷怪點編號`）時，要逐一追出值域，確認碰不到目標欄位。
- **條件旗標**：Construct 條件陣列的 `data[5]` 是「反向」旗標、事件區塊 `v[2]` 是 OR 區塊（由 `c3runtime.js` 的 `Condition`／`EventBlock` 建構子確認）。漏看會把「非開發模式」讀成「開發模式」。
- **資料表**：功能需要 15 個來源以外的資料表（例如 `zddt.json` 地圖表）時，不要併入 catalog 的 `fingerprints`／`batch2Fingerprints`：`migration-proof` 固定核對 15 項，建置閘門也比對完整指紋。改在功能自己的 catalog 區塊另記檔案雜湊；靜態快取沒有該檔時沿用同版本的舊區塊；區塊改變就關閉旗標。名稱的繁體對照手動插入 `traditional-names.json`（Windows 不跑 Swift 轉換）。
- **自訂座標**：原本「未辨識」的欄位，自訂座標可以直接寫；新功能要把它們標成已知唯讀，旗標才擋得住。
- **Shell 引號**：用 Git Bash 的 `node -e "…"` 寫 Markdown 時，反引號會被當成指令替換，把文件寫壞。含反引號的文字改用 Edit 工具或 heredoc（`<<'EOF'`）。

### 進行中狀態、凍結的複本與共用還原群組（v2.21 教訓）

- **進行中狀態**：要改「流程進行到一半」的狀態（例如渡劫進度）之前，先查它是存檔欄位還是全域變數，以及 `存档` 有沒有讀它。渡劫中的五個變數都不存檔，讀檔時就被取消，所以沒有東西可改。
- **凍結的複本**：原生流程把一筆資料搬進另一層之後就不再修改（例如入體內丹 z9→z17），那層的值只能對照「當初的原生狀態」來改。先找出真正的讀取者（`角色资质上限倍率` 只讀 y15），但同一個公式寫出的重複欄位（y16、y17）也要一起寫，否則修改器自己的紀錄檢查會拒絕。
- **共用還原群組**：會移動其他功能上限的修改（例如倍率 M），放進受影響欄位所屬的還原群組（`aptitude:角色ID`）。這樣單格還原會整組撤回，不會留下丹藥 B 超過上限的狀態。
- **重用原生備料**：需要特殊狀態的冒煙，先找既有的原生備料存檔（例如 `pill-ascended-20261024/ascended`），複製到新資料夾當 `--save-file`，不用重新備料。

### 類別欄、隱藏讀取者與同面板分派（v2.22 教訓）

- **類別和種類是兩欄**：wp 第 4 欄是種類（`宝物`、`内丹`），第 5 欄是類別（`装备`、`内丹`）。內丹的類別不是「裝備」，`词条洗练` 只收類別「装备」，所以內丹詞條一直是 0；修改器的一般裝備入口也因為 `category!=='裝備'` 擋掉內丹。判斷資格時兩欄都要看。
- **找讀取者不能只看屬性計算**：等級除了進 `装备属性计算`，還進 `内丹破镜值`，再經 `总渡劫值` 推渡劫進度。要列出所有讀取者並逐一確認效果和原生升級相同，才算沒有副作用。
- **原生備料與編輯分兩支腳本**：先用 `innerPillPrepare` 以 `获得物品` 的品質／等級參數做出要測的物品（這是原生取得路徑，不是手寫欄位），存檔讀回後把 `game/save/ea1save.dat` 複製出來當基準，再跑編輯冒煙。被搬過的列 y0 可能重複（兩顆內丹都是 7），不要要求 y0 唯一。
- **「從修改值繼續」的原生對照**：降級後直接呼叫原生 `升级装备`，比對等級 +1 與魂魄扣除量＝`升级装备魂魄`；升到上限的再呼叫一次，確認等級與魂魄都不動。
- **同一面板、不同入口**：新功能要放進既有面板（例如裝備等級）時，在 UI 依範本種類分派到新的具名入口，不改共用的 `editingInfo`／`setEditingValue`。

### 函式參數、沿用冒煙存檔與面板內的獨立資格（v2.23 教訓）

- **函式參數要數全**：Construct 函式把迴圈計數等區域變數也宣告成參數（`内丹属性计算` 有 9 個，後 7 個是計數）。`call()` 少傳時不會報錯，而是回傳 null。先從 `g.project[6]` 找 `v[0]===4` 且 `v[1][0]` 為函式名的節點，讀 `v[1][2]` 的參數清單，或照抄 `属性计算` 裡的呼叫式，再寫冒煙。
- **沿用上一版冒煙的遊戲寫出存檔**：上一版冒煙最後由原版存檔寫出的 `game/save/ea1save.dat`（連同 `saveinfo.dat`）已經有要測的狀態（例如結丹 3 次），就直接複製到新資料夾的 `savedir/ea3save.dat` 當 `--save-file`，不用重新備料。
- **同一面板、不同資格**：新功能放進既有面板，但資格比原功能寬（例如有名角色也能改入體內丹等級，結丹品質卻只開範本 0）時，新入口自己判斷資格，不要依賴原功能的 info；面板在原功能不適用時，改用新入口的資料產生共用的選擇器。

### 條件裡的讀取、沒有呼叫者的函式與原生研究接續（v2.24 教訓）

- **`g.reads` 不含條件**：`inspectGame` 的 `reads` 只收 expression 裡的 `At`，`save Arr.CompareXYZ` 這類條件讀取不在裡面（例如 `建筑等级解锁判断`、`刷新研究页面` 對 `[t,4,0]` 的檢查）。列讀取者時要另外掃事件的條件與動作（`basic-tech-20261024/cmp.cjs`），也要找以常數參數呼叫的檢查函式（`科技解锁判断(26)`）。
- **先查函式有沒有呼叫者**：研究文件寫的「控制上限」的函式可能根本沒人呼叫（`建筑最高等级`）。找出真正的讀取者再談上限或降級，取捨會差很多。
- **前置鏈與整組還原**：會連帶解鎖其他列的修改（前置科技），整條鏈放同一個還原群組，否則單格還原會留下「有後續、沒前置」的原生做不出的狀態。
- **原生接續用既有選取工具**：要證明「原生流程接受修改後的狀態」，沿用 `verify-native-lifecycle.cjs` 的 `selectFacility` 選書院研究設施，呼叫 `科技研究` 再 `取消设施进程`，同時核對旗標、設施進程與銅錢退回；已掌握的科技呼叫一次確認不會被推到 2。

### 原生上限藏在介面、下游還原與冒煙備料（v2.25 教訓）

- **上限不只看公式**：建築升階的科技式允許到 5 級，但 `刷新底部菜单` 只在 `等級 < 4` 時顯示升階按鈕，動畫（`data.json` 的 `project[3]` 物件動畫名，例如 `聚义厅0`–`聚义厅4`）與 `山寨营房人数` 也只到 4。查上限時，一併看介面按鈕條件、動畫清單與查表函式的分支數，取最嚴的那個。
- **一次 grep 全部事件**：把每個事件的條件與動作攤成一行一筆（`building-level-20261024/dumpall.cjs` → `all.txt`），再 grep `, 5, 1)`、`CALL 函式名` 或 `"按鈕狀態"`，比逐一印函式快，也不會漏掉 `g.reads` 不收的條件讀取。
- **修改會放寬其他功能的上限時**：被放寬的功能（進階科技、操練上限）如果是逐項分組，就在它的寫入入口判斷「新值是否只在新上限內」，用 `cell(m.original, …)` 算原始上限；是的話改進建築的群組。超過新上限的（進階模式）本來就不依賴建築，留在原群組。
- **基準缺前置數值時用既有編輯補**：基準存檔的進階科技都太低，冒煙情境先用既有、已驗證的 `setAdvancedTechnologyLevel`（進階模式）調高，再做新功能的編輯；不要手寫存檔欄位。
- **接續升階的原生對照**：`建筑升阶` 之後立刻 `取消升阶`，核對旗標、工程量（`建造工程量(t, L+1)`）、材料扣除與退回；城牆是立即升階，改用「在科技上限被拒」加上 `城墙升级` 在放寬後的上限內成功。
- **既有一般上限的怪癖**：`editingInfo` 在書院／校場等級為 0 時給的一般上限是 0（原生是 59／10）。合成測試的建築從 1 級起算，才測得到群組判斷；要修這個怪癖要另外確認。

### 狀態搬層、凍結的地圖與原生蓋建築（v2.26 教訓）

- **先確認狀態在哪一層**：擺放中的靈物由 `灵物库存入` 整列搬到 z19，z18 那列清空；查「已擺放」不能只看 z18 y12。開工前用呼叫閉包列出搬移函式，再決定要改哪一層。
- **凍結時間前地圖還沒生成完**：`verify-game.cjs` 一進 `主界面` 就把時間設成 0，`生成主地图建筑` 中途的 Wait 還沒跑完。剛載入時只有 3 個地圖建築、0 個建築核心，地塊實例變數（例如地塊靈氣）也還沒算。要讀地圖物件或地塊值、或要挑空地塊時，先呼叫 `verify-native-lifecycle.cjs` 的 `settleMap`（讓時間走 5 秒再凍結）。
- **Array 寫入**：Construct Array 的 SDK 寫入是 `a.Set(x,y,z,val)`，沒有 `SetAt`。只在重現原生流程的結尾步驟時使用（例如 `采集核心碰撞` 把工程量歸零後呼叫 `建筑建造成功`），並在實作摘要寫明跳過了哪一段。
- **原生蓋建築**：`生成单体建筑(範本,0,0,3,'主地图',true,X,Y,false,false,false,0,false,false)` 建出施工中的列；新列號從 z1 找新出現的範本。`relicStandPrepare` 是範例，備料後照常存檔、新 PID 讀回，再複製遊戲寫出檔當基準。
- **效果核對用修改器預測當期望值**：產生情境的腳本用 core 的預覽（例如 `aura`）算出期望值寫進原生情境檔，原生端逐地塊比對，範圍外要求為 0；不要在工具裡另寫一份公式。
- **反引號再提醒**：這次又在 Git Bash 的 `node -e "…"` 寫入含反引號的 Markdown，四份文件被寫壞，靠 `git checkout` 還原。含反引號的內容一律先用 Write 寫成腳本檔再執行。

### 只驗證不加功能、介面篩選與重啟競態（2026-10-25 靈物合成與精煉教訓）

- **先查下游真正讀了哪一欄**：精煉只讀靈物 y4，完全不讀五行；合成把 y10 存進裝備 y26，但 y26 沒有讀取者。查清楚以後，冒煙只要斷言搬移與欄位寫入，不必另算效果。
- **直接呼叫原生函式會跳過選取介面**：`套装合成`、`内丹精炼` 只檢查序號、類別與費用；材料種類、部位、靈物範本（`合成灵物编号`）與配方解鎖都只在 `刷新物品选择`／`刷新合成页面` 檢查。冒煙腳本要自己斷言這些條件，否則可能用介面選不到的組合跑出「通過」。
- **基準存檔的靈物不一定對得上配方**：T1 內丹配方全部要求獸血（妖狐靈火），所以修改過的幻魅狐印不能拿去精煉。先用 wp 第 21 欄與 lw 第 3／5 欄對配方，再在同一個情境用修改器改一顆對得上的靈物。
- **銅錢與材料數量不要放進 `state.cells`**：讀檔到凍結時間之間的每秒事件可能改動它們，只在動作裡比對扣除量。
- **`--stop` 之後馬上 `--restart` 可能失敗**：`taskkill /F` 回來時程序可能還沒退出，`--restart` 會報 `Stop the disposable process before restarting`。冒煙腳本裡要重試 restart（例如最多 10 次、每次間隔 1 秒）；半途失敗就清掉 stage，從 `--setup` 重跑。`--artifacts` 目錄要先建好。
- **反引號第三次**：這次在 heredoc 產生的 JS 範本字串裡放了沒跳脫的反引號；語法錯誤讓腳本整個沒執行，所以沒寫壞檔案。含反引號的文件段落直接用 Edit 工具寫。
