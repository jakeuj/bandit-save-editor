# 原生教訓

[維護索引](../maintenance.md) · [輕量開發流程](lightweight.md) · [遊戲改版](game-update.md)

各版實作與隔離遊戲冒煙踩過的坑，依主題重排；每條括號內是來源版本。新功能做完後，把可重用的教訓寫回本頁對應主題（[輕量開發流程](lightweight.md#session-與授權)）。

## 冒煙工具

冒煙可沿用 `verify-game.cjs --scenario`（`setPillAptitudeBonus`、`setEquipmentLevel` 等具名操作）加 `verify-native-lifecycle.cjs`（`ascend`、`followup`、`pills`、`pillOverLimit`、`backpackOverLimit`、`relics`、`relicTakeOff`、`relicStandPrepare`、`placedRelicAura`、`wall`、`city`、`ascensionQuality`、`innerPillPrepare`、`innerPillLevel`、`ascendedInnerPillLevel`、`relicCrafting`、`recruitTechnology`、`affixPrepare`、`affixOverLimit` 等動作，以 `main()` 的清單為準；`pills` 可用 `pillCharacter` 指定角色；擺放類動作要在存檔重啟後另跑一次取下，才算驗過兩輪 IO；`穿戴装备` 後要等一拍再讀角色指標，同一次 evaluate 內讀到的是空列）；固定基準存檔先複製到 repo 外的新資料夾，步驟依 `.local/game-sources.json` 的 `nativeSmoke` 紀錄（雲存檔載入 → 存檔 → assert → stop → restart → 存檔載入 → assert）。

- **只驗 Mac 啟動器、還沒改版時**：複製目前 catalog，只把 15 個來源指紋換成新版（`c3runtime.js` 用原始指紋）存到 repo 外當 `--catalog`，加 `--package` 指 Steam 安裝目錄。這只證明能存讀，不代表修改器支援新版（V1.0.13.0 Mac 補驗）。
- **函式參數隨版本變多**：V1.0.13.0 的 `穿戴装备`／`卸下装备`／`装备库存入`／`装备库取出` 末尾多了庫序號（7 背包、22 武庫），工具的呼叫都補了 `7`；少傳時是 0，函式整個不動作也不報錯。武庫的原生動作用 `armory`（`仓库存入`／`仓库取出`，換裝模式先 `a.Set(37,1,0,1)`，再用庫序號 22 穿卸）（V1.0.13.0）。
- **成本公式的原生核對**：`soulUpgrade` 讀 catalog 的 `treasureLevel.cost.growth`，從修改後等級呼叫 `升级装备` 一次，同時核對扣費＝公式與＝原生 `升级装备魂魄`。基準存檔沒有寶物或內丹時，先用 `innerPillPrepare`（寶物給 `slot: 6`）原生取得並穿上、存檔重啟當基準，再跑修改與核對（V1.0.14.0）。
- **Mac 遊戲寫出的存檔檔名帶反斜線**：重讀遊戲寫出檔要讀副本 `game/` 下的 `save\ea1save.dat`，不是 `game/save/ea1save.dat`（V1.0.13.0）。
- **背包裝備可能帶殘留歸屬**：基準存檔的背包列 y7 可能不是 0（之前換裝留下的），修改器會拒絕編輯（「歸屬為 0」）。挑 y7=0 的列；要多件時，用前一個原生動作搬回背包的新列號接著跑下一個動作（V1.0.13.0 的 `armory` 接在 `backpackOverLimit` 後面）。
- **zsh 寫冒煙腳本**：`V="node …/verify-game.cjs"` 再 `$V --setup` 不會斷詞，要寫成函式；`--setup` 的 `STATE` 那行要用 `sed -n 's/^STATE //p'` 取，不要取最後一行。setup 失敗時遊戲可能已經啟動，先查 `runs/` 裡的 state 接著跑或停掉，不要直接重跑（V1.0.13.0 Mac 補驗）。
- `verify-game.cjs` 的 `editSave` 每次都會改角色 1（等級、y50 歸零、名稱與經驗），所以要測的狀態放在別的角色（v2.16）。
- `--setup` 在讀 `--scenario` 前就建好副本目錄；情境檔路徑錯時，要清掉殘留目錄再重跑（v2.16）。
- 半途失敗時，遊戲內狀態已經變了，不要在同一副本續跑，從 `--setup` 重來（v2.16）。
- **`--stop` 之後馬上 `--restart` 可能失敗**：`taskkill /F` 回來時程序可能還沒退出，`--restart` 會報 `Stop the disposable process before restarting`。冒煙腳本裡要重試 restart（例如最多 10 次、每次間隔 1 秒）；半途失敗就清掉 stage，從 `--setup` 重跑。`--artifacts` 目錄要先建好（靈物合成與精煉）。
- `verify-game.cjs` 要等版面進入 `主界面` 才凍結時間（SetTimeScale 0），載入到凍結之間可能已經跑過一次每秒事件。目前生命低於上限時，新 PID 讀回的引擎值會多一次回血，`--assert` 的引擎比對就不會過。這時改看遊戲寫出的存檔與修改器重讀；若要讓 `--assert` 能通過，就讓該欄位在存檔時已在穩定點（例如生命已滿），或者不把它放進 observe（v2.19）。
- **凍結時間前地圖還沒生成完**：`verify-game.cjs` 一進 `主界面` 就把時間設成 0，`生成主地图建筑` 中途的 Wait 還沒跑完。剛載入時只有 3 個地圖建築、0 個建築核心，地塊實例變數（例如地塊靈氣）也還沒算。要讀地圖物件或地塊值、或要挑空地塊時，先呼叫 `verify-native-lifecycle.cjs` 的 `settleMap`（讓時間走 5 秒再凍結）（v2.26）。
- **銅錢與材料數量不要放進 `state.cells`**：讀檔到凍結時間之間的每秒事件可能改動它們，只在動作裡比對扣除量（靈物合成與精煉）。
- **刷新會改的計數不要斷言**：`新刷新招募数据` 抽到目標品質時會把 `[等階,43,0]` 保底計數歸零，`主动寻访` 加的 1 不一定留得住；只在同一次 evaluate 內比對銅錢扣除（v2.29）。
- **布林全域變數是 0／1**：`SetBoolVar` 寫進去的是數字，`global('游戏暂停').GetValue()` 回 0，不是 false。用 `assert.equal(x,false)` 會誤判成「暫停中」，連跑兩輪冒煙都失敗；斷言一律看真假值。先在現場讀值（repo 外 `probe-pause.cjs`）才發現。`System.Every` 下的每秒事件只在 `游戏暂停` 為否時跑，原生動作要 `SetTimeScale(1)` 再 `pause()` 讓時間走（v2.29）。
- **函式參數要數全**：Construct 函式把迴圈計數等區域變數也宣告成參數（`内丹属性计算` 有 9 個，後 7 個是計數）。`call()` 少傳時不會報錯，而是回傳 null。先從 `g.project[6]` 找 `v[0]===4` 且 `v[1][0]` 為函式名的節點，讀 `v[1][2]` 的參數清單，或照抄 `属性计算` 裡的呼叫式，再寫冒煙（v2.23）。
- 事件表的 static local（例如 `渡劫结丹品质`）不在 `GetAllGlobalVariables()`，要從 `GetAllLocalVariables()` 依名稱找，名稱須唯一（v2.16）。
- **Array 寫入**：Construct Array 的 SDK 寫入是 `a.Set(x,y,z,val)`，沒有 `SetAt`。只在重現原生流程的結尾步驟時使用（例如 `采集核心碰撞` 把工程量歸零後呼叫 `建筑建造成功`），並在實作摘要寫明跳過了哪一段（v2.26）。

## 基準存檔與原生備料

### 基準存檔缺狀態時先原生備料（v2.16）

固定基準存檔沒有要測的狀態（例如結丹角色）時，不要手寫存檔欄位。先用一次隔離副本做原生備料：雲存檔載入，接著用 `verify-native-lifecycle.cjs` 呼叫原生函式做出狀態（`ascend` 是範例：`获得物品`→`穿戴装备`→設定變數後呼叫 `渡劫结束`），然後原生存檔、新 PID 讀回。最後把該副本的 `save/ea1save.dat`（連同 `saveinfo.dat`）複製到 repo 外，作為新的 `--save-file` 基準，再照常跑編輯冒煙。原生行為和預期不同時（例如重生只清第一筆入體內丹），先在現場讀值確認，再決定是修正拒絕條件還是工具斷言，並把它寫進實作摘要。

### 備料的做法與沿用

- **原生備料與編輯分兩支腳本**：先用 `innerPillPrepare` 以 `获得物品` 的品質／等級參數做出要測的物品（這是原生取得路徑，不是手寫欄位），存檔讀回後把 `game/save/ea1save.dat` 複製出來當基準，再跑編輯冒煙。被搬過的列 y0 可能重複（兩顆內丹都是 7），不要要求 y0 唯一（v2.22）。
- **重用原生備料**：需要特殊狀態的冒煙，先找既有的原生備料存檔（例如 `pill-ascended-20261024/ascended`），複製到新資料夾當 `--save-file`，不用重新備料（v2.21）。
- **沿用上一版冒煙的遊戲寫出存檔**：上一版冒煙最後由原版存檔寫出的 `game/save/ea1save.dat`（連同 `saveinfo.dat`）已經有要測的狀態（例如結丹 3 次），就直接複製到新資料夾的 `savedir/ea3save.dat` 當 `--save-file`，不用重新備料（v2.23）。
- **沿用上一版的備料存檔，要拿未編輯版**：v2.30 的 `prepared/` 是原生備料、還沒編輯過的存檔；`smoke/final` 已經有超限係數，拿來當基準會被修改器拒絕（v2.31）。
- **基準缺前置數值時用既有編輯補**：基準存檔的進階科技都太低，冒煙情境先用既有、已驗證的 `setAdvancedTechnologyLevel`（進階模式）調高，再做新功能的編輯；不要手寫存檔欄位（v2.25）。
- **基準存檔沒有要測的物品**：先用 core 掃一遍候選存檔（repo 外 `affix-overlimit-20261025/list2.cjs`），全部都是 Q1 才用 `affixPrepare` 原生取得、穿戴、洗練。`获得物品` 的參數同 `innerPillPrepare`（品質、等級、等階、`装备主属性系数(Q,'')`）；穿戴用 `wp` 第 6 欄當部位，會把原本那件換回背包（v2.30）。
- **基準存檔的靈物不一定對得上配方**：T1 內丹配方全部要求獸血（妖狐靈火），所以修改過的幻魅狐印不能拿去精煉。先用 wp 第 21 欄與 lw 第 3／5 欄對配方，再在同一個情境用修改器改一顆對得上的靈物（靈物合成與精煉）。
- **原生蓋建築**：`生成单体建筑(範本,0,0,3,'主地图',true,X,Y,false,false,false,0,false,false)` 建出施工中的列；新列號從 z1 找新出現的範本。`relicStandPrepare` 是範例，備料後照常存檔、新 PID 讀回，再複製遊戲寫出檔當基準（v2.26）。

## 找讀取者與寫入者

- **先用呼叫閉包核對「某原生流程不碰哪些欄位」**：要把既有功能放寬到新狀態（例如結丹角色）時，先確認造成該狀態的原生流程不寫功能依賴的欄位，就能沿用原本的見證與交易，不必重做規則。做法：用 `scripts/extract-game.cjs` 的 `inspectGame` 讀本機來源，從 `g.project[6]` 找出函式事件（`v[0]===4` 且 `v[4]` 等於 `g.functions` 的 sid），沿 `-2`／`5` 的函式呼叫 action 求出呼叫閉包；再把閉包內函式在固定座標索引（例如 `candidate-sweep-20261023/index.json` 的 `operations`／`reads`）的寫入依 z、y 過濾。閉包會多算 UI 刷新函式，沒關係；要另外看動態 y 的寫入落在哪些 z，並在實作摘要寫明固定座標索引的限制。腳本放 repo 外（v2.18）。
- **一次 grep 全部事件**：把每個事件的條件與動作攤成一行一筆（`building-level-20261024/dumpall.cjs` → `all.txt`），再 grep `, 5, 1)`、`CALL 函式名` 或 `"按鈕狀態"`，比逐一印函式快，也不會漏掉 `g.reads` 不收的條件讀取（v2.25）。
- **`g.reads` 不含條件**：`inspectGame` 的 `reads` 只收 expression 裡的 `At`，`save Arr.CompareXYZ` 這類條件讀取不在裡面（例如 `建筑等级解锁判断`、`刷新研究页面` 對 `[t,4,0]` 的檢查）。列讀取者時要另外掃事件的條件與動作（`basic-tech-20261024/cmp.cjs`），也要找以常數參數呼叫的檢查函式（`科技解锁判断(26)`）（v2.24）。
- **動態座標**：`inspectGame` 的 `reads` 會記下 x 為 `*` 的讀取，但寫入的 y 是動態運算式（例如 `39+任命序號`、`21+刷怪點編號`）時，要逐一追出值域，確認碰不到目標欄位（v2.20）。
- **條件旗標**：Construct 條件陣列的 `data[5]` 是「反向」旗標、事件區塊 `v[2]` 是 OR 區塊（由 `c3runtime.js` 的 `Condition`／`EventBlock` 建構子確認）。漏看會把「非開發模式」讀成「開發模式」（v2.20）。
- **寫入者要看在哪個分支**：之前的靜態補查記「`获得物品` 初始化 y14／y20 寫 0」，追祖先條件才發現那是內丹分支，普通裝備從不碰第六槽。列寫入者或讀取者時，用 repo 外 `quality7-20261025/ctx.cjs <sid>`（讀 `all.txt` 與 `nodes-index.json`）把祖先事件的條件一起印出，確認是哪一類物品、哪個 `$方式`（v2.31）。
- **找讀取者不能只看屬性計算**：等級除了進 `装备属性计算`，還進 `内丹破镜值`，再經 `总渡劫值` 推渡劫進度。要列出所有讀取者並逐一確認效果和原生升級相同，才算沒有副作用（v2.22）。
- **讀取者要追到包裝函式的呼叫者**：欄位只被 `角色资质计算` 讀，但「上限」藏在呼叫它的地方（`刷新丹药` 的條件、主事件服藥按鈕、`服用普通丹药` 的前置條件）。`g.reads` 只看到包裝函式本身，所以要再 grep `building-level-20261024/all.txt` 的 `fn:包裝函式名`，逐一確認每個呼叫者遇到超限值是夾住、拒絕還是照算（v2.27）。
- **讀取者先找效果函式的所有參數值**：科技等級只經 `加成属性效果(24)` 進招募倒數，但 `加成属性效果` 也被 `属性计算` 以 `sx` 第 12 欄的變數參數呼叫。把 `all.txt` 裡 `fn:加成属性效果(…)` 的參數全列出來，再查變數參數的資料表有沒有指到同一個編號，才算讀取者找齊（v2.29）。
- **先查函式有沒有呼叫者**：研究文件寫的「控制上限」的函式可能根本沒人呼叫（`建筑最高等级`）。找出真正的讀取者再談上限或降級，取捨會差很多（v2.24）。
- **先查下游真正讀了哪一欄**：精煉只讀靈物 y4，完全不讀五行；合成把 y10 存進裝備 y26，但 y26 沒有讀取者。查清楚以後，冒煙只要斷言搬移與欄位寫入，不必另算效果（靈物合成與精煉）。
- **修改器自己也是讀取者**：原生端找齊後，再 grep `src/` 有沒有用同一個值域公式檢查這個欄位（這次是 `60+10*q`）。`ordinaryEquipment` 檢查每一槽係數，被 `characterAptitudeSource` 用來檢查穿戴裝備，所以一件超限裝備會連帶擋掉穿戴者的丹藥、基礎資質與技藝上限。放寬時加可選參數（`overLimitAffix`），只在旗標開啟、且該功能與這個欄位無關時傳 `true`；這是產品取捨，要問使用者（v2.30）。
- **類別和種類是兩欄**：wp 第 4 欄是種類（`宝物`、`内丹`），第 5 欄是類別（`装备`、`内丹`）。內丹的類別不是「裝備」，`词条洗练` 只收類別「装备」，所以內丹詞條一直是 0；修改器的一般裝備入口也因為 `category!=='裝備'` 擋掉內丹。判斷資格時兩欄都要看（v2.22）。

## 上限與值域

- **上限不只看公式**：建築升階的科技式允許到 5 級，但 `刷新底部菜单` 只在 `等級 < 4` 時顯示升階按鈕，動畫（`data.json` 的 `project[3]` 物件動畫名，例如 `聚义厅0`–`聚义厅4`）與 `山寨营房人数` 也只到 4。查上限時，一併看介面按鈕條件、動畫清單與查表函式的分支數，取最嚴的那個（v2.25）。
- **上限可能只在研究入口**：`科技等级上限` 只擋 `科技研究` 與提示，效果端 `进阶科技属性` 不夾；表格上限（`kj` 第 5 欄）也不等於效果上限。超限值的意義看效果式本身（`600−L` 沒有下限），再看其他入口的條件（`主动寻访` 要倒數 >1）（v2.29）。
- **同一欄位，迴圈次數各不同**：生成與洗練頁是 `Repeat(装备词条数量(Q))`（夾到 5），`装备属性计算` 與 `物品tips` 是固定 `Repeat 6`。所以「原生到不了」和「讀到了會不會照算」是兩件事，讀取者的迴圈上限要逐一看（v2.31）。
- **介面值超出分支時看動畫清單**：`SetAnim` 的名稱來自數值（品質 7 → `"7"`）時，從 `g.project[3]` 找物件，`o[7]` 是動畫清單；c3runtime 的 `_DoChangeAnimation` 找不到名稱就直接 return，顯示會停在預設動畫。字串函式沒有命中分支時回空字串，所以品質字樣會變空白（v2.31）。
- 修改一個值、連帶影響另一個狀態時（例如降級後目前生命會不會超過上限），除了查寫入者，也要查**有沒有原生流程會把它拉回範圍**。城牆的回血與治療都只在「低於上限」時觸發，沒有流程會往下壓，所以降級必須自己處理生命（v2.19）。

## 狀態所在層與衍生值

- **先確認狀態在哪一層**：擺放中的靈物由 `灵物库存入` 整列搬到 z19，z18 那列清空；查「已擺放」不能只看 z18 y12。開工前用呼叫閉包列出搬移函式，再決定要改哪一層（v2.26）。
- **進行中狀態**：要改「流程進行到一半」的狀態（例如渡劫進度）之前，先查它是存檔欄位還是全域變數，以及 `存档` 有沒有讀它。渡劫中的五個變數都不存檔，讀檔時就被取消，所以沒有東西可改（v2.21）。
- **凍結的複本**：原生流程把一筆資料搬進另一層之後就不再修改（例如入體內丹 z9→z17），那層的值只能對照「當初的原生狀態」來改。先找出真正的讀取者（`角色资质上限倍率` 只讀 y15），但同一個公式寫出的重複欄位（y16、y17）也要一起寫，否則修改器自己的紀錄檢查會拒絕（v2.21）。
- **衍生快取**：改了來源值（例如城市層數），要查衍生快取（例如總聲望 `[8,1,0]`）**讀檔時會不會重算**。總聲望只在 `获得声望` 重算，讀檔不會；擴張門檻又只讀快取，所以修改器必須在同一筆交易依原式重寫快取。冒煙時用 `call('重算函式',…)` 比對修改器寫入值，不要只比自己的公式（v2.20）。

## 原生對照與效果核對

- 修改器算不準的原生值（例如含科技與司職加成的 `城墙最大生命`），冒煙時直接在現場用 `verify-native-lifecycle.cjs` 的 `call('函式名')` 取回傳值，和修改器的下界或預期值比對；不要在工具裡重寫一份加成公式（v2.19）。
- **效果核對用修改器預測當期望值**：產生情境的腳本用 core 的預覽（例如 `aura`）算出期望值寫進原生情境檔，原生端逐地塊比對，範圍外要求為 0；不要在工具裡另寫一份公式（v2.26）。
- **效果核對用就地差值**：在同一次 evaluate 內呼叫原生函式，用 `a.Set` 把該槽改回原值再呼叫一次，然後寫回。差值和修改器預覽的 `effect.delta` 比對，就不必管同屬性的其他來源；寫回後讀一次確認（v2.30）。
- **超限後原生會怎麼反應，用對照組證明**：只斷言「服藥被拒」可能是工具呼叫錯；同一個動作裡加一項仍在上限內的資質，確認同樣的呼叫會扣丹藥、加增量，拒絕才有意義（v2.27）。
- **看不出差別的重設用標記**：L=599 時每秒都重設成 1，倒數值本身無法分辨「有沒有跑」。在只有重設分支會寫的欄位（`[11,1,0]`）先寫標記 7，跑時間後確認被清成 0；對照組（L=450）標記保持 7，結束時寫回原值（v2.29）。
- **「從修改值繼續」的原生對照**：降級後直接呼叫原生 `升级装备`，比對等級 +1 與魂魄扣除量＝`升级装备魂魄`；升到上限的再呼叫一次，確認等級與魂魄都不動（v2.22）。
- **接續升階的原生對照**：`建筑升阶` 之後立刻 `取消升阶`，核對旗標、工程量（`建造工程量(t, L+1)`）、材料扣除與退回；城牆是立即升階，改用「在科技上限被拒」加上 `城墙升级` 在放寬後的上限內成功（v2.25）。
- **原生接續用既有選取工具**：要證明「原生流程接受修改後的狀態」，沿用 `verify-native-lifecycle.cjs` 的 `selectFacility` 選書院研究設施，呼叫 `科技研究` 再 `取消设施进程`，同時核對旗標、設施進程與銅錢退回；已掌握的科技呼叫一次確認不會被推到 2（v2.24）。
- **直接呼叫原生函式會跳過選取介面**：`套装合成`、`内丹精炼` 只檢查序號、類別與費用；材料種類、部位、靈物範本（`合成灵物编号`）與配方解鎖都只在 `刷新物品选择`／`刷新合成页面` 檢查。冒煙腳本要自己斷言這些條件，否則可能用介面選不到的組合跑出「通過」（靈物合成與精煉）。

## 修改器設計

- **共用還原群組**：會移動其他功能上限的修改（例如倍率 M），放進受影響欄位所屬的還原群組（`aptitude:角色ID`）。這樣單格還原會整組撤回，不會留下丹藥 B 超過上限的狀態（v2.21）。
- **前置鏈與整組還原**：會連帶解鎖其他列的修改（前置科技），整條鏈放同一個還原群組，否則單格還原會留下「有後續、沒前置」的原生做不出的狀態（v2.24）。
- **修改會放寬其他功能的上限時**：被放寬的功能（進階科技、操練上限）如果是逐項分組，就在它的寫入入口判斷「新值是否只在新上限內」，用 `cell(m.original, …)` 算原始上限；是的話改進建築的群組。超過新上限的（進階模式）本來就不依賴建築，留在原群組（v2.25）。
- **同一面板、不同入口**：新功能要放進既有面板（例如裝備等級）時，在 UI 依範本種類分派到新的具名入口，不改共用的 `editingInfo`／`setEditingValue`（v2.22）。
- **同一面板、不同資格**：新功能放進既有面板，但資格比原功能寬（例如有名角色也能改入體內丹等級，結丹品質卻只開範本 0）時，新入口自己判斷資格，不要依賴原功能的 info；面板在原功能不適用時，改用新入口的資料產生共用的選擇器（v2.23）。
- **自訂座標**：原本「未辨識」的欄位，自訂座標可以直接寫；新功能要把它們標成已知唯讀，旗標才擋得住（v2.20）。
- **資料表**：功能需要 15 個來源以外的資料表（例如 `zddt.json` 地圖表）時，不要併入 catalog 的 `fingerprints`／`batch2Fingerprints`：`migration-proof` 固定核對 15 項，建置閘門也比對完整指紋。改在功能自己的 catalog 區塊另記檔案雜湊；靜態快取沒有該檔時沿用同版本的舊區塊；區塊改變就關閉旗標。名稱的繁體對照手動插入 `traditional-names.json`（Windows 不跑 Swift 轉換）（v2.20）。
- **既有一般上限的怪癖**：`editingInfo` 在書院／校場等級為 0 時給的一般上限是 0（原生是 59／10）。合成測試的建築從 1 級起算，才測得到群組判斷；要修這個怪癖要另外確認（v2.25）。

## 測試陷阱

登記規則見[輕量開發流程的「測試也不綁目前 core」](lightweight.md#測試也不綁目前-core)。

- core 以 `vm` 載入，回傳的陣列屬另一個 realm，`assert.deepEqual` 會報「same structure but are not reference-equal」；先展開（`[...x]`）或只比長度再比較。
- 重抽 `catalog.json` 時鍵順序可能和既有檔不同，以語意比對確認沒有其他差異即可。
- **改到共用樞紐**：改到 `editingInfo`、`setEditingValue` 這類共用樞紐（v2.14 背包超限）時，所有 family 的切片都會變，`migration-proof` 的 `problem()` 對歷史證明一律回「複合證明與來源或程式不相符」。比照「測試也不綁目前 core」：直接斷言「開放群組的證明對上目前 core」的測試改成只核對群組紀錄；要測證明結構檢查（缺首次紀錄、交換、資料雜湊）的測試，用 `tests/helpers/current-core-proof.cjs` 把複本的 core 身分換成目前來源再測。換身分後原生證據摘要仍綁舊切片，所以不能再斷言整體 `problem()` 為 null。
- **既有小數旗標會改一般模式的上限**：`pillAptitudeBonusDecimal` 開啟時，`pillInfo.max` 是一位小數（例如 15.5），不是整數 15。測試斷言一般上限前先確認哪些旗標開著（v2.27）。
- **旗標決定走哪條分支**：`pillAptitudeBonusAscended` 開啟時，丹藥改走 `aptitudeNeutralEquipment`，完全不看係數，所以「穿戴者丹藥被擋」的測試要先關掉它。寫測試前先確認目前 catalog 開著哪些旗標會改走另一條路（v2.30）。
- **瀏覽器規格不要點停用中的按鈕**：Playwright 會等到逾時。要證明「不合法值不能套用」，只填值，再斷言按鈕停用與提示文字（v2.30）。
- **模擬測試的答案佇列**：同一個 test 裡連跑幾次被拒絕的案例時，前一次失敗會在佇列留下沒用到的答案；每次執行前先清空（`answers.length = 0`）（v2.30）。
- **`#pendingCount` 數的是儲存格**：一次寫兩格（ID 與係數）的操作會讓計數加 2，瀏覽器規格要照格數斷言（v2.31）。

## Shell 與寫檔

- **反引號（四次教訓）**：含反引號的 Markdown 或程式範本不要經過 shell 字串或外層範本。
  - Git Bash 的 `node -e "…"` 會把反引號當成指令替換，把文件寫壞（v2.20）；v2.26 又因此寫壞四份文件，靠 `git checkout` 還原。
  - heredoc 產生的 JS 範本字串裡放了沒跳脫的反引號，語法錯誤讓腳本整個沒執行，所以沒寫壞檔案（靈物合成與精煉）。
  - 想用 `String.raw` 拼出含 `${}` 的 UI 範本，外層模板會先求值，腳本直接語法錯誤（v2.27）。
  - 做法：含反引號的文件段落直接用 Edit 工具寫；需要腳本時先用 Write 寫成腳本檔再執行，shell 只用單引號 heredoc（`<<'EOF'`）；改 UI 一律用 Edit 工具逐段替換。
- Git Bash 的 `node -e` 寫檔要用 `H:/...`，不能用 `/h/...`（v2.16）。
- 背景指令裡用 `tail -3 a b` 會失敗（要寫 `tail -n 3`），整個背景任務因此被標成失敗，但冒煙本身已通過，要看 steps.log 判斷（v2.28）。
