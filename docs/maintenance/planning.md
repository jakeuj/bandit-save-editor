# 進度查詢與下一版承接

[維護索引](../maintenance.md) · [下一步與目前進度](../research/next-version-plan.md)

## 單一入口與分工

- **next-version-plan.md**：使用者與 agent 的第一入口；只維護目前主線、階段、已完成摘要、下一個具體任務、阻擋／待決事項、提案／任務／證據連結及本機／提交／發布狀態。
- **目前 SDD 的 proposal.md／tasks.md**：規格與逐條進度／驗收依據，任務編號須可直接續做。
- **feature-roadmap.md**：候選優先順序及歷史研究理由，不當作目前執行佇列。
- **研究文件**：來源、公式、靜態／原生證據與 go／no-go；Project 是任務追蹤鏡像，Wiki 是公開導覽，均不另定實作優先順序。

## 按使用者問法承接

1. 「現在做到哪／下一步做什麼」：讀目前進度及其主線 SDD，再核對工作樹與最近提交。簡短回答目前階段、已完成、下一個未完成任務、是否有阻擋，附同一入口；不要重新盤點整個候選列表，也不要因問進度而開始寫功能。
2. 「繼續實作下一版功能／開始實作」：目前入口若只有一個主線且提案足以執行，這句就是對該提案的實作確認；直接讀提案與任務，從第一個未完成項接續，不再次詢問要做哪個功能或是否可以實作。先核對既有成果及來源；沒有證明的群組仍保持關閉。
3. 「繼續」：延續當前對話已授權階段。只完成研究、尚未獲實作指示時，不將此字自動擴成核心實作授權；先完成研究範圍內尚缺的工作。階段或目標確實有多個可能才問必要問題。
4. 沒有目前主線、提案缺關鍵決策、或原生結果推翻規格時，先把可確認部分與下一個具體決策寫回入口；不要用歷史 prompt、候選排序或私人卡片內容推導新授權。

實作指示涵蓋提案內必要的合成／隔離驗證，不自動延伸為遊戲桌面 UI、真實雲端／成就、發布或其他候選。提交推送沿用當前任務有效授權；已明確授權不重問，舊版本紀錄不當成永久發布授權。

## 每次停點與交付

先更新 tasks.md 的真實完成項及證據，再更新目前進度的摘要與下一項。記錄以下資訊即可：

- 當前主線／階段、下一個未完成任務編號及可執行動作。
- 阻擋與解除條件；沒有阻擋就寫清楚，不製造待核准項。
- 已完成驗證的精確範圍；未完成的原生／UI／部署分開列。
- 本機未提交、已提交、已推送、已發布分開標示；repo 外 state 只在本機索引記路徑，公開文件不放玩家或機器私密資訊。

摘要與 SDD／工作樹衝突時，先核對證據修正，不重做已有完成證據的階段。研究結論改變（例如寶物不是經驗制）時，同步 roadmap 的現行描述與技能功能入口，保留舊證據的歷史標記。

完成一案後將已發布／已歸檔紀錄移入概況，指定下一個建議候選與所需研究；候選未被選定前，不假裝它已開始。外部 Project／Wiki／公告預設不同步，使用者要求時才更新；公開導覽始終連回同一進度入口。
