需求類型：新功能。研究日期：2026-10-22（Asia/Taipei）。狀態：**2026-10-22 A 階段完成待驗收，採建議決策；B尚未實作，功能未開放**。

提案階段僅調查與建立本案 proposal／tasks；不修改產品、catalog、驗證旗標或既有 SDD，不啟動 Steam／遊戲、不做隔離遊戲驗證、不推送。使用者說「實作」並確認下方決策及拆分後才進入下一階段。本機提交可行，GitHub 推送仍須另問。

## 為什麼做

v2.7 已發布一般隨機角色基礎資質；路線圖第 2 項的下一步為九項技藝上限。一般隨機角色的範本為 0，不進入有名角色的載入回填分支，但這只支持存檔修改的可行性，不能直接支持任意數值、任意九項組合或後續遊戲行為。

本版提供有原版生成依據、可預覽且能完整還原的上限調整。v2.9 合法天賦編輯另案；本版只會唯讀使用判斷上限組合所需的天賦資料。

## 已確認的靜態事實

### 欄位、型別與九項共同生成

角色編號 `r`、技藝 `k=1–9`，座標從零起算：

| 欄位 | 座標 | 本版型別與用途 |
| --- | --- | --- |
| 上限 C | `[r,21+k,2]`，即 y22–30 | 原版 round／clamp 產生數值整數；一般模式要求原始欄位及輸入都是安全整數 |
| 等級 L | `[r,30+k,2]`，即 y31–39 | 正安全整數；上限交易保留，不藉此降級或升級 |
| 餘額 E | `[r,39+k,2]`，即 y40–48 | 有限、非負數值；原生結算會 floor 舊餘額，不能把字串或未知值轉成合法數值 |

1–9 為伐木、採礦、種植、鍛造、工藝、煉丹、建造、研究、操練；第 10 項會撞到既有經驗欄位，必須拒絕。

重新解析目前原始 `新刷新招募数据` SID `390673545485827`，一般隨機角色分支為 `908961798874365`。子事件 `495736577950540` 從 1–9 等權選主要技藝；`449071711713692`／`156638308886716` 從其餘八項等權選次要技藝，兩者不可相同。`333798278035776` 先寫九項一般值，再覆寫主要、次要各一項：

- 一般值：`clamp(round(6 + 3Q + random(-5,5)), 1,100)`。
- 主要值：`round(23 + 10Q + random(-15,5))`。
- 次要值：`round(15 + 8Q + random(-14,4))`。

random 上界開放；經 round 後兩端整數都有非零寬度的原像。Q1–Q6 的一般分支尚不會觸發 1／100 截限。由公式推導的閉整數區間如下，**不是已完成隔離實測的矩陣**：

| Q | 七項一般值 | 一項主要值 | 一項次要值 |
| --- | --- | --- | --- |
| 1 | 4–14 | 18–38 | 9–27 |
| 2 | 7–17 | 28–48 | 17–35 |
| 3 | 10–20 | 38–58 | 25–43 |
| 4 | 13–23 | 48–68 | 33–51 |
| 5 | 16–26 | 58–78 | 41–59 |
| 6 | 19–29 | 68–88 | 49–67 |

因此不能用九項各自 1–100 的檢查，也不能把九項都設成主要值。Q6 的一般隨機角色在本次公式下最高為 88；舊文件「角色初始化可能超過 100」是較廣的角色範圍，不能直接套到本案範本 0 的招募規則。一般／次要區間可能重疊，不能單靠排序或最大兩欄推定唯一主次。

原始主要／次要與招募傾向為招募函式局部變數；此子樹未將它們另存為持久欄位。需要枚舉 9×8 個有序主次位置找見證，不假造可編輯的「主要技藝 ID」。初始等級另由各 cap 的 0.3–0.45 倍亂數加偏移、clamp 後 floor 生成；已養成角色不再要求等級回到這個初始比例，只要求本版提交後不低於目前等級。

### 品質、傾向、基礎資質與天賦的相依

品質直接改變三種區間；傾向沒有直接出現在上限公式或主次抽選權重中。Q1 使用「通用」，Q2–Q6 原始傾向為力量／敏捷／智力／生產；戰鬥傾向在資質分配後，還依最大權重更新為對應傾向（`208593979189941`、`140851839037360`、`626958821361227`、`283020746938208`）。條件的 OR 設定也已回查原事件，不能把多個 Compare 誤讀成 AND。

天賦是在上限之後抽取，不參與上述上限算式，卻限制哪些主要位置能與現有天賦共同生成：

- 招募子樹 `873825376472526` 以三個已選 ID 去重；tf 的有效 ID、原始分類／傾向及 `tf[id,12+主要技藝] != 1` 共同決定候選。
- 通用傾向：`591767082846289`／`292760985647917`；戰鬥傾向讀 tf 第 6 欄（`838299876826997`／`831316140562000`／`645593055477100`）；生產讀第 4 欄（`782357767511312`／`307497448049499`／`176962926512198`）。均須保留原 OR 語意。
- 品質天賦等級池依序為 1–2、1–3、2–4、3–5、4–5、5。這裡只查既有天賦能否作為生成見證，不開放 ID／等級編輯，也不做 v2.9 全效果研究。
- 現有 `batch2Data.talents` 只有效果屬性與係數，沒有上述候選欄位；v2.8 必須由 tf 生成最小唯讀選取資料，不能以「catalog 收錄該 ID」代替合法組合檢查。

**建議的一般模式語意：**同品質，存在與目前三項基礎資質及三槽天賦相容的傾向、主要／次要見證，能生成目標九上限。預覽說明這是固定基礎／天賦下的上限組合見證，不保證角色全部歷史狀態可由一次新招募生成。等級、丹藥、裝備等已可能由後續遊玩改變，不強制回到新招募狀態。

替代方案是只驗「同品質九上限子向量可生成」，不約束固定基礎／天賦；成本較低，但可能接受與現有天賦衝突的主要位置，介面只能宣稱上限子向量合法。**不建議默採此方案。**使用者需決定證明界線；完整相容方案須補精確的傾向見證，現行 `recruitmentCombination` 只回第一個可行結果，不能直接拿它當所有可行傾向清單。

v2.7 本來接受同品質任一資質傾向，沒有驗整組天賦選取相容性；因此 v2.7 可改的角色，不保證本版新操作一定有共同見證。遇到無見證只停用 v2.8 並顯示原因，不回寫或自動修復資質／天賦。合法 `0/0` 空槽與原版完整三槽招募可生成也要區分；首版建議無完整見證即停用，不擅自補天賦。

### 與經驗結算的差異

`获得技艺经验` 的 `727573628418621` 在 **呼叫開始 L<C** 時加 E；`927397704806210` 達需求就扣一次並加一級；其兄弟 Else `275143275632288` 在原本已到 cap 的分支清 E。由控制流程推導：剛升到 cap 的該次呼叫可能仍留餘額，下一次已封頂呼叫才清零。**本輪未用原生程序確認這個時序，列為優先隔離案例，不把路線圖的「達上限歸零」當作立即清零證明。**函式還會按工作類型重設獲得量為 10 並套加成，不可假設傳入的大數值會原樣增加。

目前 `src/core.js` 的 `addExperience` 則 floor 舊 E，加正整數 amount，逐級扣需求，結算到 cap 立即 E=0。這是既有直接經驗／批次 API 的規則；本案保留此規則，不以調 cap 偷做一次經驗結算。

| 目標狀態 | 建議行為 | 理由及替代方案 |
| --- | --- | --- |
| 目標 C<L | 整筆阻擋 | 不偷偷降級；不提供強制寫入 |
| 目標 C=L，E=0 | 可接受，仍須整組生成見證 | cap 操作不改 L／E |
| **下調**至 C=L，E>0 | 首版整筆阻擋 | 替代為明示「餘額 E→0」正規化交易，會丟失餘額，需另加確認、獨立案例及完整還原；本提案建議延後 |
| 提高 C，原本 L=舊 C、E>0 | 保留 E，不立即升級 | 後續 `addExperience` 依既有 floor／逐級／封頂規則結算；原生按一次工作事件結算，兩者分開比對 |
| C>L，E為非負小數或已足升級 | cap 交易保留原 E，不替遊戲結算 | 不把既有餘額當新增經驗；後續呼叫才依各自規則處理。須有原生與合成代表案例 |
| 所有輸入等於目前值 | 不寫 token、不新增歷史、不清 E | 即使既有封頂 E>0，也不能用無變更操作偷偷正規化 |

原生可留封頂餘額不代表修改器一定要允許「下調製造封頂餘額」；首版阻擋是產品保守政策，須在提示中說明，不能偽稱原版永遠沒有此狀態。若原生驗證與時序推論不符，先回到規格決策，不靠清零掩蓋差異。

## 要改什麼

### 資格與排除範圍

- 僅有效已招募角色，序號符合目前列、範本數值恰為 0、品質數值整數 1–6、y55=0、y50=0 且 z16 y1–16 全零；身份／狀態欄型別錯誤不強轉。
- 九 cap、L、E 均可辨識，L≥1、cap≥L，必要資質／天賦資料足以建立選定語意的共同見證；目前 cap 已超範圍或無見證時先停用，不提供修復模式。
- y50／z16 與在監限制是首版證明範圍，不宣稱它們直接參與技藝 cap 公式。後續若要擴張，另補證明。
- **不機械沿用** v2.7 丹藥整數、持有丹藥、普通穿戴、內丹／套裝資質來源與 A／B／C 計算限制；cap 公式不依賴這些。小數丹藥或穿戴特殊裝備本身不應使本功能停用。所需基礎資質只讀 raw 的生成相容性，不計算裝備／丹藥後的資質。
- 自動轉職 y59 是既有職業經驗限制，不直接套為技藝 cap 限制；本版不改 y59、不代做轉職。
- 有名角色顯示「載入／數值更新會依角色範本回填技藝上限」，明確停用。招募候選、未招募、在監、階段紀錄、天賦編輯、超限、角色生成及 runtime 補丁均排除。

### API 與預覽交易

建議新增下列具名 API；名稱與固定參數為契約，不開任意座標、方法名稱或可執行的預覽清單：

| API | 固定請求／回應 |
| --- | --- |
| `randomCharacterSkillCapsInfo(model,{characterId})` | 資格、逐項原因、品質、九組 C／L／E、可行見證及獨立 verified 狀態 |
| `previewCharacterSkillCaps(model,{characterId,caps})` | `caps` 固定九個數值安全整數；回九列 before／after、全部聯動差異、阻擋原因、見證、unchanged／canApply 及不可偽造的預覽關聯 |
| `setCharacterSkillCaps(model,{characterId,caps},{preview})` | 僅接受相符且未過期的核心預覽關聯；重新計算資格、組合、欄位型別及閘門，再原子提交一次；不信任呼叫者修改的 differences |

選擇九項整組提交。使用者可以只改一格，但每次送完整九項再驗證共同主次見證；一次提交只增加一筆歷史，並不一次寫入全部九個 token。單項獨立 API 容易讓連續修改的中間狀態不合法，故首版不提供。

預覽使用私有 WeakMap／等效不可偽造關聯，記錄模型身份、原文、變更／歷史版本、請求及驗證／規則狀態；輸入、選角色、換檔、任何模型變更、還原／復原或閘門變更都使其失效。提交必須取得新檢查結果；偽造、跨模型、已用過或過期預覽不得提交。可沿用批次 API 的快照概念，不把其內部座標執行器公開化。

首版只有 cap token 差異，L／E 每列仍完整顯示「保持」；若未來選擇正規化，E差異必須出現在同一筆預覽與確認中。失敗回復變更、歷史、分組與交易計數，不因失敗留下一半標記。同值不增加歷史。保留未修改原始字元、大型整數 literal、BOM、空白、CRLF 及指數寫法，沿用 token serializer，禁止整份 JSON stringify 後匯出。

`resolveField` 明列 y22–48 的具名操作與關聯；`setField`、舊 `set`、自訂座標及匯入舊設定皆不能繞過。特別補無效／未啟用角色列的已知 cap／L／E 座標覆蓋，避免 `activeCharacter` 分支外被當成未知數值而走舊 set。

### 累計還原及 v2.6 相容

建議在**本次載入期間第一次有效上限調整**時，讓此角色的九 cap＋九 L＋九 E 進入同一個 `skill-growth:角色ID` 累計還原群組（27 欄）。理由是九上限共同生成，且上限與經驗互相制約；逐技藝三欄分組仍可能還原出不存在主次見證的九上限。

此時需吸收該角色先前單項／v2.6 批次技藝經驗的累計差異；之後 `addExperience(kind:'skill')` 與九技藝批次都沿用此群組。群組是否已啟用不能只由「目前有沒有 cap 差異 token」推定，因 cap 可能改回原值但經驗仍有差異；私有相依標記亦須進入交易快照與 undo。沒有做過 cap 交易的角色維持現有逐技藝還原；其他角色、有名角色的原本經驗資格及閘門不擴張。

現行 `restore`／`undo` 只處理changes Map，UI「還原全部」直接清Map；新增相依標記後須讓三者一起恢復，不能只補cap setter。全部還原後是否回到未啟用群組的載入狀態亦納入測試；undo還原全部時，須能完整找回原群組標記與差異。

驗證順序含：經驗→cap→經驗、cap→九項批次→再改cap、兩角色交錯、cap回原值後仍有經驗差異、從 cap／L／E 任一差異入口個別還原、還原全部及逐次 undo。個別還原回載入基準的整組，不能留下超 cap 等級；undo 回上一筆交易並恢復當時群組模式，不回到載入基準。還原群組可能比玩家預期大，介面先明示「此角色全部技藝上限與經驗會一起還原」。

v2.6 仍固定透過 `addExperience` 處理九項、任一失敗整批不改、成功一筆 undo；先前的批次預覽在 cap 改動後失效。cap 群組關閉不應停用原本合法的技藝經驗操作；skillExperience 關閉也不得被 cap API 偷呼叫或當作零額正規化入口。

### 介面
