# 山寨帳房 v2.9「一般隨機角色天賦」

需求類型：新功能。研究日期：2026-10-23（Asia/Taipei）。狀態：**2026-10-23 使用者核准，見[已核准決策](#已核准決策2026-10-23)；任務見 [tasks](tasks.md)，尚未實作。** 提案階段未修改產品、catalog、verification 或旗標，未啟動遊戲。

靜態研究與逐題證據見 [天賦前置研究](../../docs/research/random-character-talents.md)；排序與前置條件見[後續版本計畫](../../docs/research/next-version-plan.md)第 2、3、5 節。

## 為什麼做

v2.7 開放範本 0 角色的基礎資質，v2.8 開放九項技藝上限，兩者都只把 z12 y1–3／21–23 的三槽天賦當唯讀條件。天賦是一般隨機角色剩下的生成欄位；玩家最常見的需求是把低品質招募的天賦等級補到同品質上限，其次才是換掉不想要的天賦。

## 基準與證據界線

| 項目 | 結果 | 可支持的結論 |
| --- | --- | --- |
| 來源 | V1.0.11.2 repo 外精簡解包，13 指紋與 catalog 相符；V1.0.10.2 對照的 tf 與 5 個天賦子樹摘要相同 | 規則跨兩版穩定；不代表原生實測 |
| 生成規則 | 品質等級池、三類傾向篩選、主要技藝排除、三槽互異都已逐事件核對 | 與 v2.8 `skillCapCombinations` 的篩選一致 |
| 效果 | `天赋属性` 有 6 個公式分支，107 個屬性槽，不寫存檔 | 需要獨立 oracle；不能沿用「level×coefficient/10」 |
| 範圍 | 只考慮範本 0、非在監、無結丹／重生紀錄的已招募角色（同 v2.7／v2.8 資格） | 有名角色由 `数值更新` 回填，不在範圍 |
| 權限 | 24 群組，沒有 `randomCharacterTalents` | 需新群組與首次完整證明 |

## 三種範圍政策

共同前提：只接受原版可生成的值。等級須在該品質池（Q1 1–2、Q2 1–3、Q3 2–4、Q4 3–5、Q5 4–5、Q6 5），ID 須為 1–75、三槽互異、符合傾向與主要技藝排除，且不寫 0/0。

### L：只改等級（建議首版）

- 狀態空間：每角色 Q1 8、Q2–Q4 各 27、Q5 8 種；Q6 只有 5 級，沒有可改值。
- 原生 oracle：75 天賦共 107 個屬性槽×5 級＝535 個 `天赋属性计算` 值，一個隔離程序內完成，與 v2.5 的 6,592 組公式比對同類。
- 角色矩陣：Q1–Q5×3 槽×升／降＝30 角色（槽位選擇須覆蓋 6 個公式分支、單／雙屬性），另 3 角色分別帶 ID 1／2／3 驗資質與丹藥上限連動，再加 2 角色生命週期（數值更新不回填、轉職、下獄／召回、重生、解雇）。合計約 **33＋2**。
- v2.7 影響：只有 ID 1–3 會改 A 與 C；新 C 低於既有丹藥 B 時阻擋。
- v2.8 影響：ID 不變、等級仍在池內，傾向／主要技藝推論不變，**共同見證不會因此消失**；只需確認核心見證函式仍接受新等級。

### I：只改 ID

- 狀態空間：5 傾向×9 主要技藝＝45 類；池大小 55（Q1 通用）／47（戰鬥）／21（生產），有序三槽組合 157,410／97,290／7,980。
- 原生 oracle：同 535 值。
- 角色矩陣：6 品質×9 主要位置＝54 角色，每角色替換一槽為池邊界 ID（例如戰鬥角色取分類為生產、傾向為通用的天賦；生產角色取分類為通用的天賦；Q1 取任意未排除 ID），另 6 角色覆蓋 ID 1–3 及雙屬性；不合法替換（重複、跨傾向、排除主要技藝）只需 Node 負向測試。合計約 **60＋2**。
- v2.7 影響：增刪 ID 1–3 會改 A 與 C，同 L。
- v2.8 影響：改 ID 會改變可行的 (傾向, 主要)。必須以「固定資質＋九上限＋新三槽」重算聯合見證，沒有見證就阻擋；接受後的角色必然仍有技藝上限見證。

### LI：ID 與等級都改

- 狀態空間：I 的空間再乘以等級池。
- 角色矩陣：可把 L 的升降併入 I 的 54 角色（每角色同時改 ID 與等級），再補 Q6 唯讀與資質連動，約 **60–90＋2**，接近 v2.8 的 108＋2。
- v2.7／v2.8 影響：同 I。

## 建議決策

1. 首版採 **L**；I／LI 在 L 發布後另開。
2. 天賦 6 欄與 v2.7 的 `aptitude:角色ID` 6 欄合併為 12 欄累計群組（因為 ID 1–3 會改 C，B≤C 是硬限制）。v2.8 `skill-growth:角色ID` 27 欄維持獨立；undo 仍回上一筆交易。
3. 不提供 0/0「清除天賦」。
4. UI 只宣稱存檔與原生計算；名稱／tips 截圖只作可選觀察，不當開閘條件。
5. 不提供天賦批次。

## 對共同見證與核心摘要的影響

- 任何 `src/core.js` 位元變動都會讓 `randomCharacterSkillCaps` 的整檔 `formulaHash` 失效（計畫第 2 節第 2 條）。v2.9 A 必然改 core，所以**技藝上限群組要跟著重開**。v2.8.1 已於 `9167e3f` 發布並完成自己的重開；v2.9 應在 A 凍結 core 後只重開一次，B 不再改 core。
- v2.7 `randomCharacterBaseAptitudes` 與 `equipmentQuality` 只綁公式片段；v2.9 不得改到 `scripts/random-character-growth-proof.cjs` 列出的 core 區段，否則 v2.7 也要重驗。
- 新規則摘要須涵蓋研究第 7 題列出的 SID；v2.8 的選取規則已在其摘要內，不必補。

## A／B 拆分

**A：核心與 Node（不開閘門）**

- 新最小規則產生器：tf 第 4–12 欄、sx 第 4 欄型別、6 個公式分支、品質等級池；綁 `sourceSids` 摘要，未知摘要拒絕產生。
- 核心三具名 API：`randomCharacterTalentsInfo`、`previewCharacterTalents`、`setCharacterTalents`；私有預覽關聯與 revision 重驗，只寫有差異的 token。
- 12 欄合併群組、undo、`restoreAll`、v2.6 批次暫存模型相容。
- 需求表、suite family（`initialProofRequired`、`pendingReason`）、代表情境與相依宣告同步，原生 oracle／lifecycle 為明確失敗的入口。
- Node 合成測試：池內／外、Q6 唯讀、資質上限阻擋、v2.8 見證保持、BOM／大型整數 literal 保留。

**B：介面、原生證明與發布**

- 角色養成頁的三槽等級編輯器，預覽後明確套用。
- 535 值原生 oracle、33 角色矩陣、2 角色生命週期，逐階段原版存檔與新 PID 讀回。
- 重開技藝上限群組（隨 core 變動），首次證明合併時保留其他群組紀錄逐項不變。
- 瀏覽器回歸（HTTP 1280／390px、直接 file、PWA）、更新紀錄、發布核對。
